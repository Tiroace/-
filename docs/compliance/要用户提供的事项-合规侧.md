## 五、2026-11-03 补充：截图删除口径 —— **我此前结论有误，已更正**

### 更正说明（重要）

我 11-03 上午在本文件写的结论是「应用层 23h ＋ 每小时扫描 ＝ 最坏 24h 内删，不用改」。**这个算法是错的。**

**产品经理指出后我重新穷举验证，他是对的。** 关键在：`expires_at = 上传时刻 + 23h`，但清理线程按固定 3600s 周期跑，**扫描点相对每次上传时刻的相位是任意的**。删除发生在「上传时刻 + 23h 之后的第一个扫描点」：

| 扫描相位 | 实际删除于上传后 |
|---|---|
| 0s | 24.00 h（刚好卡线） |
| 600s | 24.17 h |
| 1800s | 24.50 h |
| 3599s | **约 25.00 h** |

→ **大多数情况下会超过 24 小时，最坏接近 25 小时。** 「24 小时内删除」这句**目前不成立**，必须改。

### ✅ 已定案（D36，2026-11-03）：不用改代码，改措辞

**结论：采用方案 A。** 隐私政策已改为「**24 小时内进入删除流程，最迟 25 小时内删除完毕**」（`01-隐私政策草稿.md` L14 / L36 / L84 / L186）。理由：与现有实现完全一致，**零改代码、绝不说谎**，且「进入删除流程」＋「最迟 25 小时」把真实机制说清楚了。

**⚠️ C1 已结案，不需要用户拍板。** 任何人不要再把它当待办去问用户。
