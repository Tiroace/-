# 社区模块补齐计划（D7 之后，不占引擎主线）

- 依据：老板 2026-10-31 19:10 拍板；社区模块 7 项核对结论见群消息。
- 原则：**排在 D7 交付之后**，不占用识别引擎/提审主线时间；订阅消息、异步自动审核等**依赖正式 AppID/资质**的项，等 AppID 下来再做。

## 二、举报自动隐藏的复核与恢复（老板新增要求）

现在的问题：举报满 3 次直接把帖子置 `hidden`，**没有复核步骤，也没有恢复入口**，会被恶意举报压帖。

改法：
1. 举报触发隐藏时，同时写入复核标记（如 `posts.needs_review=1`、`hidden_reason='reported'`），并记录触发时间。
2. 管理端审核列表新增队列 `status=needs_review`（或 `queue=report`），把被举报隐藏的帖子单独列出。
3. 新增恢复动作 `action=restore`：`hidden` → `approved`，记录处理人/时间；**保留举报计数与举报明细**（便于识别人恶意举报），帖子重新可见。
4. 复核维持隐藏时 `action=hide`，同样记录处理人/时间/理由。
5. 同一帖子恢复后再次被举报满阈值，仍要重新进队列（不能因已恢复过就跳过）。
6. 权限：恢复只能由管理员令牌操作；写审计日志（见第 3 项）。

测试用例（测试者补）：
- 3 个账号举报 → 状态 `hidden` 且出现在复核队列；
- 管理端 `restore` → `approved`、列表可见、举报明细仍在；
- 恢复后再次举报满 3 次 → 再次 `hidden` 并再进队列；
- 非管理员调 `restore` → 403；
- 每次隐藏/恢复都产生一条操作日志。

## 三、发帖页文案

- 设计稿原文「审核通过后公开，一般几分钟内完成」→ **只保留「审核通过后公开」**（当前源码里没有这句，前端补一行说明；等异步自动审核上线后再改回）。
- 禁止出现「几分钟内完成」这类时效承诺。

## 四、操作日志字段（第 3 项）

`admin_audit_log`：id、operator（管理员标识）、action（approve/reject/hide/restore/ban/unban/appeal_resolve/sensitive_words_update）、target_type（post/experience/appeal/user/sensitive_words）、target_id、detail（JSON：理由、前后状态）、created_at。
保留期：**≥6 个月**（原型 SQLite 不自动清理；上 MySQL 后由定时任务按 6 个月归档/删除）。
