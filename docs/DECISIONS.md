## 详细记录：D30 / D31（产品口径）

### D30 · 「无经验 + 月入 X」高薪诱饵：统一判黄（pay 维度）

**状态**：**已执行**（2026-10-31，标注 + 规则同一次提交 5d018e4；见下方实测结果）

**背景**：同一句 `无经验骑手、月入9000元` 在两批样本里等级不同——RT0067/0068/0069（岗位名「销售代表」）标 `red/pay=red`；RT0118/0119/0120（岗位名「储备干部」）标 `amber/title=amber`。两份 OCR 除岗位名一行外逐字相同（已核对，见 `data/testset/ocr/RT0067.txt` 与 `RT0118.txt`）。

**决定**：统一判黄，维度统一 `pay`。六条样本 `overall=amber`，`dimensions` 为 `{fee:none, work:none, title:none, pay:amber, company:none, contract:none}`。

**理由**：

1. **只有一句高薪承诺，没有第二条证据。** 判红意味着「建议先别去」，必须有硬证据（收费、贷款、刷单、扣押证件这类触碰法律底线的）；「无经验却开高薪」是夸大宣传，判黄更匹配信息强度。
2. **判红会让 09 类规则自相矛盾。** `14` 号话术审定表把「无经验开高薪」定为 `R-BAIT-01` 黄；样本标红等于规则说黄、标注说红，只能靠 `escalate_regex` 打补丁，而这个补丁正是矛盾的来源。
3. **要判红必须有独立于薪资的第二条证据。** 「无经验 + 月入 9000」同时出现「先交押金 / 先垫钱 / 办贷款 / 下陌生 App 领任务」时，`fee`/`work` 硬规则会自然把整体拉红，不需要高薪这一句单独判红。

**随之要做**：

1. 标注：RT0067/0068/0069 的 `overall` 与 `pay` 从 `red` 降为 `amber`；RT0118/0119/0120 的 `title→none`、`pay→amber`。六条之后完全一致。
2. 规则：`R-BAIT-01` 去掉 `escalate_regex`，保持 `level: warn`；`说明` 里「升红」说法一并改掉。

**实测结果**（执行后，`eval/eval_real_text.py` split 分开报）：

| --- | --- | --- |
| practice 102 条 整体 | 99.0% | **100.0%** |
| holdout 27 条 整体 | 92.6% | **100.0%**（验收线 95%，达标） |
| practice 六维 | 86.8% | **87.1%** |
| holdout 六维 | 87.0% | **89.5%** |
| 合成 20 条 / 反例 / selftest / smoke | 100%/0%误判、15/15、76/76、108/108 | **不变** |

**执行中多修了一处**：`R-DISCRIM-01`（疑似歧视）的 `keywords` 里混着 `无经验骑手`——和性别/婚育/地域歧视毫无关系，
是早前为凑 `title` 维度误加的。D30 把 `title` 归 `none` 后它立刻显形（六条全部 `title` 报黄）。已删除该关键词，
`R-DISCRIM-01` 回到 17 条真正的歧视话术。**这是规则里的真错，不是标注问题。**

**关于「储备干部」**：岗位名本身可疑，但正文没有「实际做销售/地推」这类职责描述，`title` 不给黄灯是对的。**岗位名可疑 ≠ 名实不符**，后者必须有职责原文佐证。

### D31 · 六维归属：一事一灯，按「该维度写了什么」判

**状态**：已定，作为规则与标注的共同依据。

**一句话**：一条话术只点亮一盏灯，点哪盏由「这句话在说哪个检查项」决定，不由「这句话有多可疑」决定。同一句话牵涉两维时，按主维度优先级 `fee > work > contract > pay > title > company` 取最高。

**依据**：六维一致率 86.8%，60 处差错方向是「引擎判红但标注 none」，根因是同一件事被归到不同维度（例：「可在国家电网/部队文职安排工作」引擎记 `title`、标注记 `fee`）。**不是规则错，是归属没定义。**

**执行**：归属表见 [`17-六维判定边界与映射表.md`](06-合规与文案/17-六维判定边界与映射表.md)（优先级规则 + 逐类话术归属说明）；规则落库时每条规则的 `dimension` 必须与表一致；标注时同一条话术的 `dimensions` 只点亮对应那一维；灰灯（`none`）含义固定为「截图里没提到这一项」，不是「这一项没问题」，也不是「这件事归到别的维度了」。

### D32 · 「口头承诺薪资但未签书面合同」：统一归 `contract`（黄）

**状态**：已定，待执行（改 RT0148/0149/0150 三条标注）

**背景**：同一句 `口头承诺支付每月薪资8000元，但未签订书面劳动合同` 在两批样本里归了不同维度——RT0028/0029/0030（岗位名「客服专员」）标 `contract=amber`，RT0148/0149/0150（岗位名「销售代表」）标 `pay=amber`。两份 OCR 除岗位名一行外逐字相同（已核对 `data/testset/ocr/RT0028.txt` 与 `RT0148.txt`），`overall` 六条都是 `amber`，只有灯的位置不同。

**决定**：六条统一 `contract`。RT0148/0149/0150 改为：

```json
"dimensions": { "fee": "none", "work": "none", "title": "none", "pay": "none", "company": "none", "contract": "amber" },
"expected_findings": [ { "dimension": "contract", "evidence": "口头承诺支付每月薪资8000元，但未签订书面劳动合同" } ]
```

RT0028/0029/0030 不动。六条 `overall` 保持 `amber`。

**理由**：

1. **这句话的核心缺陷是「没签书面劳动合同」。** 薪资 8000 元本身不异常（不是虚高，也不是区间离谱），它只是「被口头承诺」的那个对象。删掉「未签订书面劳动合同」这半句，这句话就只是一个正常薪资承诺，不值得点任何灯——**说明缺陷在合同那一半，不在薪资**。
2. **按 D31 优先级 `contract > pay`。** 同一段话牵涉两维时取最高，`contract` 在 `pay` 之上，规则本来就规定了答案，这里是标注没执行。
3. **如果归 `pay`，会让用户看错重点。** 用户看到「薪资待遇」亮黄，会以为工资有问题去问工资；实际要问的是「什么时候签正式劳动合同」。灯归哪一维，直接决定报告里给什么问题、说要怎么核实——归错维度，报告给的建议就是错的。

**随之要做**：测试者改 RT0148/0149/0150 三条标注；规则侧 `R-*` 里若有把「未签合同 + 口头承诺薪资」归 `pay` 的，同步改成 `contract`（`R-CLAUSE-01`、`P-CONTRACT-04` 归 contract 是对的，无需改）。

**这组为什么归 `contract` 而不是 `fee`**：没有任何钱从求职者口袋出去（不是收费、不是押金、不是贷款），所以不适用更高优先级的 `fee`。

**遗留观察**：本次审计修订后只剩这一组三对冲突，说明 D31 优先级表已经覆盖了绝大多数场景；后续若再出现「同一个意思两维皆可」的话术，应先在 `17` 号文档补一行映射，再改标注——**不要直接按直觉挑一维**。
