## 0. 这次要做什么

现版本功能骨架是对的，但看起来像后台表单，没有让人想用、更没有让人愿意付费的感觉。这次改版做五件事：

2. **识别引擎升级**：加「套路库」语义匹配；报告改成固定 6 个维度「逐项亮灯」，见第 4 节。
3. **换视觉**：按第 5 节「夜间信号」深色规范和 `02-设计稿图片` 重做界面。
4. **补转化页面**：新增「次数用完弹窗」「会员页」「分析中」，重做「报告页」。
5. **修 bug**：见第 3 节。
6. **新增求助广场**：用户发布公司职位求助，其他用户互相投票「建议去 / 不建议去」并分享经历，配套敏感词和风险过滤，见第 11 节。

建议顺序：改名和修 bug → 设计变量 → 首页 → 识别引擎升级（后端）→ 报告页 → 弹窗和会员页 → 我的 → 分析中 → 求助广场。前端和后端可以并行。

## 4. 识别引擎升级：套路库 + 逐项亮灯

本节替换《项目任务下派书》第 4.2 节第 4–7 步和第 4.3 节。

### 4.1 发现从三个地方来

| 来源 | 做什么 | 例子 |
| --- | --- | --- |
| 规则词库 | 关键词、正则，命中就是硬证据 | 押金、垫付、刷单、贷款 |
| 套路库匹配 | 截图里每句话和套路库里的话术样本做语义比对，像的就召回 | 「工装费入职后退」匹配「服装押金」套路 |
| 大模型推理 | 结合整张截图判断：前后矛盾、不合常理、名实不符、关键信息缺失；也判断哪些项是正常的 | 写「无需经验」，却开「月薪 8000–20000」 |

### 4.2 流程

1. OCR 识别后按句切分。
2. 规则词库扫描，命中的作为硬证据。
3. 每句做向量检索，从套路库取相似度最高的前 5 条，超过阈值的作为候选（阈值用测试集调）。
4. 把 OCR 全文、硬证据、候选套路（名称、说明、等级）、6 个检查维度一起交给大模型，输出 4.4 节的 JSON。
5. 证据校验：每条发现的 `evidence` 必须能在 OCR 原文里找到，找不到就删掉。绿灯发现也一样要有原文。
6. 等级校准：硬证据命中的维度至少是红灯；高相似度命中红灯套路的，模型不能往下调。
7. 某个维度截图里完全没提到：灰灯「截图里没提到」，并把相关问题自动加进追问清单。
8. 整体结论由后端按规则算，不让模型自己定：有任一红灯维度 → 红；否则有黄灯 → 黄；否则 → 绿；不是招聘截图或信息太少 → unknown。

### 4.3 六个检查维度（固定）

| key | 名称 | 看什么 |
| --- | --- | --- |
| fee | 收费与借贷 | 押金、培训费、贷款、垫付、索要银行卡或验证码 |
| work | 工作内容 | 刷单、拉人头、下载陌生 App、境外工作 |
| title | 岗位名称 | 名称和实际职责是否一致 |
| pay | 薪资待遇 | 区间是否离谱、底薪提成是否写清、和要求是否匹配 |
| company | 公司信息 | 有没有全称、地址；联系人是不是个人号 |
| contract | 合同社保 | 劳动合同、试用期、社保 |

上线前固定这 6 个；后台可配置，方便以后增加。

### 4.4 报告 JSON（新版）

```json
{
  "is_job_posting": true,
  "overall": "red | amber | green | unknown",
  "summary": "一句话结论，30 字以内",
  "dimensions": [
    { "key": "fee", "level": "red | amber | green | none", "short": "要先交押金" }
  ],
  "findings": [
    {
      "level": "red | amber | green",
      "dimension": "fee",
      "title": "入职前收钱",
      "evidence": "入职前需交 300 元工装押金",
      "context": "入职前需交 300 元工装押金，转正后全额退还",
      "reason": "大白话解释为什么",
      "source": "rule | pattern | llm",
      "pattern_id": "P-DEPOSIT-001",
      "rule_id": null
    }
  ],
  "questions_to_ask": ["面试前建议问 HR 的问题"],
  "how_to_verify": ["核实方法"],
  "prompt_version": "v2.0",
  "pattern_db_version": "2026-10-30"
}
```

- `dimensions` 必须 6 项都有；`short` 不超过 6 个字。
- `findings` 数量不固定，0 到多条都可以，按红、黄、绿排序。
- `title` 4–8 个字；`context` 是包含 evidence 的整句，前端用它显示原话并高亮 evidence。

### 4.5 套路库

**数据表**

| 表 | 主要字段 |
| --- | --- |
| patterns | id、名称、对应维度、等级、为什么危险、遇到了怎么办、状态（启用/停用）、来源（公开反诈案例/复核反馈/运营录入）、更新时间 |
| pattern_examples | id、pattern_id、话术原文、向量 |
| pattern_hits | pattern_id、report_id、命中时间（只记录命中，不记录用户截图） |

**怎么建、怎么长**

- 向量：用国内云厂商的文本向量接口 + 向量检索（云厂商向量检索服务，或 PostgreSQL + pgvector）。具体选型要核实费用和是否在已备案服务范围内。
- 首批：运营整理 50 个套路，每个 5–10 条话术样本，来源是公开的反诈宣传和新闻案例。
- 持续扩充：用户点「判断不准」→ 人工复核 → 确认是新套路就入库。入库后先跑一遍测试集，指标不降才生效，版本号写进报告。
- 首页「套路库里，最近常见的」和「套路」页读同一个库；「最近常见」按近 7 天的 `pattern_hits` 真实次数排序，不编数字。
- 套路库只描述话术和手法，不写具体公司名。

**评测补充**：在原测试集基础上，增加「维度级准确率」（6 个维度的灯色判对比例）和「套路库召回率」，两项指标进每次上线前的回归。

## 5. 设计规范：方案 A「夜间信号」

### 5.1 设计理念

名字里的「请等等」就是黄灯。深色背景上，红、黄、绿三个灯会「发光」，结论一眼就能看懂。

两条铁律：

- 品牌黄 `$cta` 只用在主按钮和品牌标识上。
- 红、黄、绿只用来表达风险结论和投票结果，不拿来做装饰。

### 5.2 颜色

完整变量在 `03-参考代码/design-tokens.scss`，主要的：

| 变量 | 色值 | 用途 |
| --- | --- | --- |
| $bg | #0E1620 | 页面背景 |
| $surface | #17222E | 卡片 |
| $surface-2 | #1F2C3A | 引用框、图标底 |
| $line | #263546 | 边框 |
| $ink | #F1F4F6 | 主文字 |
| $ink-2 | #93A3B1 | 次要文字 |
| $ink-3 | #C5D0D8 | 解释正文 |
| $cta | #FFC93C | 主按钮、品牌黄 |
| $cta-ink | #16120A | 主按钮上的字 |
| $housing | #0A1017 | 信号灯底座、求助卡 |
| $red / $amber / $green | #FF5A47 / #FFB21E / #34D07F | 三种灯 |
| $off | #3A4756 | 灰灯：截图里没提到 |

每种灯另有 `-soft`（浅底）、`-text`（文字）、`-mark`（原话高亮）三个变量。

### 5.3 字体与字号

用系统字体，不引入网络字体。

| 层级 | 字号 / 字重 | 用在哪 |
| --- | --- | --- |
| 首页大标题 | 34 / 900 | 「去面试之前，先让我看一眼」 |
| 结论标题 | 28 / 900 | 报告页结论 |
| 页面标题 | 26 / 900 | 会员页 |
| 弹窗标题 | 22 / 900 | 次数用完 |
| 区块标题 | 17 / 800 | 「6 项检查」「具体发现」等 |
| 正文强调 | 15–16 / 700 | 卡片标题、列表主文字 |
| 正文 | 15 / 400 | 原话、问题、核实方法 |
| 说明 | 13–14 / 400 | 副标题、解释 |
| 辅助 | 12 / 400–700 | 标签、免责声明 |
| tab | 11 / 500，选中 700 | 底部导航 |

设计稿按 390 宽画。用 rpx 实现时，数值 = 设计稿 px × 750 ÷ 390，约乘 1.92，取整即可。

### 5.4 圆角、间距、光晕

- 页面左右边距 20；大卡片圆角 24，普通卡片 20，按钮 14–16，标签 8。
- 主按钮高 56；次要按钮 44–52；任何可点区域不小于 44×44。
- 区块之间 28–32；卡片内边距 16–20；卡片之间 10–12。
- 灯的光晕：`box-shadow: 0 0 22px 灯色`，小圆点用 10–12px。光晕只给灯用，卡片不加阴影。

### 5.5 图标与品牌标识

- 线性图标，描边 1.8。参考代码里的 SVG 可以转成图片或 iconfont。不用 emoji。
- 品牌标识：黄色圆角方块 + 两根深色竖条（暂停键），代表「等等」。正式 logo 可以请设计师按这个思路精修。

### 5.6 深色模式要配套改的地方

- `pages.json`：每页 `backgroundColor` 设 `#0E1620`，`navigationBarTextStyle` 设 `white`，避免页面切换时闪白。
- 原生 tabBar：`backgroundColor #121C27`、`color #8090A0`、`selectedColor #FFC93C`、`borderStyle black`。
- 弹窗、Toast、Loading 尽量用自定义组件，平台默认的白色弹框和深色页面不搭。

### 5.7 不要做

渐变色、任何蓝色、卡片阴影、emoji、满屏小灰字、首页一打开就推会员。

## 6. 逐页说明

### 6.1 首页（设计稿 01）

- **导航栏**：`navigationStyle: custom`。左侧品牌标识 + 名称；右侧给平台胶囊按钮让位，位置用 `uni.getMenuButtonBoundingClientRect()` 算。
- **上传卡**：
  - 插画（三张截图，中间一张标出可疑行）可以导出成一张图片，也可以用 view 拼。
  - 主按钮调用 `uni.chooseImage`（相册 + 拍照，最多 3 张）。
  - 选好图后，在卡片里显示缩略图（可删除），按钮变成「开始检查（2 张）」。
  - 剩余次数从 `/me` 取；次数为 0 时点按钮，弹出「次数用完弹窗」。
- **示例报告入口**：打开报告页，加载内置示例数据（本地 JSON，内容和设计稿 02 一致），顶部加「示例报告」标识。不调接口，不扣次数。
- **信号灯说明卡**：静态内容。
- **套路库里，最近常见的**：读套路库，取近 7 天命中最多的 3 条。「全部套路」进套路页（P1）；套路页没做之前，隐藏这个入口。
- **底部 tab**：检查、广场、我的。套路页不占 tab，从首页「全部套路」进入。

### 6.2 分析中（新增，设计稿没画）

- 全屏深色页面，中间是信号灯，三个灯依次亮起循环。这是整个产品里唯一的动画。
- 文字按真实阶段切换：「正在读截图」→「正在比对套路库」→「正在逐项检查」→「正在写报告」。不做假进度条。
- 超过 30 秒：显示「有点慢，分析完会出现在检查记录里」和「先回首页」按钮。

### 6.3 报告页（设计稿 02）

**结论区**按 `overall` 换颜色和亮灯：

| overall | 背景 | 亮灯 | 标题 |
| --- | --- | --- | --- |
| red | $red-soft | 红 | 这份工作，建议先别去 |
| amber | $amber-soft | 黄 | 先问清楚，再决定去不去 |
| green | $green-soft | 绿 | 看起来没问题，可以去 |
| unknown | $surface | 三灯全暗 | 截图信息不够，再补一张 |

- 副标题统计各灯数量，比如「2 项红灯，2 项黄灯，1 项绿灯」。
- **6 项检查**：2 列网格，每格是维度名 + 小灯 + `short`。灰灯显示「截图里没提到」。
- **具体发现**：`findings` 每条一张卡，按红、黄、绿排序。卡片头部：小灯 + `title` + 来源标签（rule 显示「规则命中」，pattern 显示「套路库匹配」，llm 显示「AI 推理」）。下面是原话引用框（用 `context`，高亮 `evidence`）和解释。
- **面试前，先问 HR 这几个问题**：`questions_to_ask`。「复制」按钮把全部问题复制到剪贴板，提示「已复制，可以直接发给 HR」。
- **自己也能核实**：`how_to_verify`。
- **已经交了钱？**：只在 `overall = red` 时显示；两个按钮用 `uni.makePhoneCall` 拨 110 和 96110。
- **免责声明 + 判断不准？告诉我们**：跳反馈页，带上 report_id。
- **底部**：「提醒朋友」走平台分享，分享标题用「去面试之前，先让它看一眼」，不带任何公司名；「再查一份」回首页。

### 6.4 次数用完弹窗（设计稿 03）

- 底部弹出，背景压暗。
- **看广告**：严格按抖音流量主规范。用户点了按钮才创建广告；`isEnded` 为真时调 `POST /ad/reward`；广告加载失败或没有填充时直接给 1 次（平台要求必须兜底）。
- 「今天还能看 N 次」由服务端返回；到了当天上限，隐藏看广告这一项。
- **会员卡片**：iOS 开不了虚拟支付时，整张卡片不显示，弹窗里不能出现任何价格和付费字眼。

### 6.5 会员页（设计稿 04）

- 套餐和价格从服务端配置读，默认选中月卡。按钮文案跟着选择变：「开通周卡 ¥6.9」「开通月卡 ¥19.9」「开通季卡 ¥39.9」。
- 会员权益只写次数和保存时长，**不能出现「免广告」**（抖音明确禁止付费免广告）。
- 「一次性购买，到期不自动续费」这句必须保留。
- 支付成功：提示「会员已开通」，返回来源页。
- iOS 不支持虚拟支付时，所有会员入口都隐藏。

### 6.6 我的（设计稿 05）

- `/me` 新增 `checked_count`（查过的工作数）和 `red_count`（亮过的红灯数）。
- 会员条：非会员显示「开通会员，每天最多查 20 次」；会员显示「会员有效期至 11 月 30 日」这类到期日。
- 检查记录有数据时：每条显示整体结论的小灯 + 一句话结论 + 日期，点进对应报告；没有数据时按设计稿显示空状态。
- 菜单只保留 4 项：意见反馈与申诉、AI 服务说明、隐私政策、用户协议。
- 不要「退出登录」；「开发自测」只在开发环境出现。

### 6.7 套路页（P1，设计稿没画）

一列套路卡，样式和首页「套路库里，最近常见的」一致。点进去是详情：典型话术、为什么危险、遇到了怎么办。

### 6.8 求助广场、求助详情、发起求助（设计稿 06–08）

见第 11 节。

## 7. 为什么这样设计能让人付费

- 先让用户免费看到价值（示例报告、免费 3 次），再谈付费。
- 报告要「值钱」：6 项逐项亮灯、原话高亮、标明是套路库还是 AI 推理、法条依据、能直接复制给 HR 的问题。用户觉得这份报告有用，才会为下一份付钱。
- 有绿灯也照实说：不是一棍子打死，用户才信得过。
- 付费入口放在用户最需要的时候：次数用完、正要查下一份时。首页不推会员。
- 价格锚点用真实损失（少交一次 300 元押金就回本），不编造数据，不写「已帮 10 万人避坑」这类没有数据支撑的话。
- 不写「免广告」，不做自动续费。

## 11. 求助广场：用户互相投票

老板定的方向：用户把拿不准的公司职位发出来求助，其他用户投「建议去 / 不建议去」，并分享自己的经历。平台只提供发布和投票的地方，不替用户评价公司。敏感词和风险过滤必须做。

### 11.1 页面

- **求助广场（设计稿 06）**：
  - 搜索公司名或职位；排序：最新、参与最多、我投过的。
  - 帖子卡：公司名、职位和城市、提问、AI 检查结论、投票条和票数、投票人数和经历条数。
  - 右下角「发起求助」。
- **求助详情（设计稿 07）**：
  - 发帖人（匿名昵称）、公司、职位、提问、打码后的截图、AI 检查摘要（可点进完整报告）。
  - 投票区：「建议去 / 不建议去」两个按钮，投完可选理由标签，下方显示投票条和人数。
  - 「大家的经历」列表：显示每人投了什么、有用数、举报入口。
  - 底部：免责说明 + 企业申诉入口；输入框「说说你的经历」、举报、分享。
- **发起求助（设计稿 08）**：
  - 必须关联一份检查记录；没有就先上传截图做检查。
  - 自动打码预览，用户可以点图片补充打码。
  - 公司名称（从截图识别，可改）、职位和城市、提问（最多 200 字）。
  - 填写提示：写事实，不写「骗子」这类结论。
  - 匿名发布（默认打开）；「确认是真实经历并已阅读社区规范」必须勾选。
  - 按钮「提交审核」。

### 11.2 投票规则

- 每个账号对每个帖子只有一票：建议去或不建议去，可以改，不能重复投。
- 发帖人不能给自己的帖子投票。
- 理由标签选填：我也被要求过交钱、岗位和说的不一样、面试流程正常、其他。标签后台可配置。
- 显示票数和比例条。不把票数换算成公司评分，不做公司排行榜和黑名单页。
- 新注册未满 24 小时的账号，不能投票、发帖、写经历。
- 防刷：同一设备、同一 IP 段短时间大量投票的进入风控，可疑票不计入展示，但保留记录备查。

### 11.3 风险过滤：发布前、展示中、事后三道

| 环节 | 做什么 |
| --- | --- |
| 发布前：敏感词 | 敏感词库 + 大模型审核两层。辱骂、人身攻击、色情暴力、违法有害信息直接拦截；「骗子」「黑心」这类定性词，提示用户改成描述事实，改完才能提交。词库后台可随时增删，不用发版 |
| 发布前：隐私打码 | 截图 OCR 后自动打码手机号、微信号、QQ 号、身份证号、银行卡号、人名、门牌号；文字里出现的同类信息替换成 *** |
| 发布前：内容安全 | 图片和文字都走平台的内容安全检测接口 |
| 发布前：审核 | 先审后发：机器审核通过即发布，拿不准的进人工审核 |
| 展示中 | 帖子和经历都标明「来自用户分享，只代表个人经历」。可以显示公司名；AI 检查结论只针对截图内容，不对公司下结论 |
| 事后：举报 | 每个帖子、每条经历都能举报。同一内容被举报达到 3 次（可配置）先自动隐藏，再人工复核 |
| 事后：企业申诉 | 企业上传营业执照认证后申诉。目标 24 小时内处理，结果为保留、修改或删除，通知发帖人，处理记录长期保存 |
| 事后：违规处理 | 多次违规的账号禁言或封号 |

### 11.4 数据表

| 表 | 主要字段 |
| --- | --- |
| posts | id、user_id、匿名昵称、report_id（关联检查记录）、公司名、职位、城市、提问、打码后图片地址、状态（审核中/已发布/已隐藏/已删除）、创建时间 |
| votes | post_id、user_id、选择（建议/不建议）、理由标签、更新时间；post_id + user_id 唯一 |
| experiences | id、post_id、user_id、内容、状态、有用数、创建时间 |
| reports | 举报：对象类型、对象 id、举报人、原因、处理结果、处理时间 |
| appeals | 企业申诉：企业名、认证材料、对象 id、处理结果、处理人、处理时间 |
| sensitive_words | 词、级别（拦截/提示改写）、更新时间 |

### 11.5 和套路库联动

- 帖子关联的 AI 检查命中了哪些套路，计入 `pattern_hits`。
- 一个帖子「不建议去」占多数、而且理由集中（比如大多选「我也被要求过交钱」），进人工复核池；复核确认是新话术，就加进套路库。
- 这样，一个人踩的雷会变成之后所有人报告里的红灯。

### 11.6 对外开放前要核实（开发可以先做，功能开关默认关闭）

- 用公司主体；小程序类目要选允许用户发布内容的类目，并满足它的资质要求。
- 用户发布内容、可以投票的社区，是否需要信息发布类增值电信业务许可、是否要做安全评估，请律师和平台确认。
- 后台实名（手机号或平台实名），前台可以匿名。
- 求助广场页面先不放广告，降低流量主违规风险。
- 用户协议、社区规范、隐私政策写清楚：内容由用户发布并负责，平台收到侵权通知后会及时处理。
