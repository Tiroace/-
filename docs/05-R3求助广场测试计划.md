# R3 求助广场 · 测试计划与用例（先于接口编写）

- 编写：软件测试者
- 版本：v0.1（2026-10-31）
- 依据：任务书 §11（求助广场）、§11.2 投票规则、§11.3 风险过滤三道、§11.4 数据表、§9 验收第 15–19 条
- 状态：**接口未就绪，本文件先定「怎么判过关」**；开发者出接口后按此直接落成 pytest

> 为什么先写计划：社区是「用户产生内容 + 公开可见 + 可举报他人」的模块，
> 一旦规则漏洞上线，影响的是**名誉风险和监管风险**，比识别准确率更硬。
> 所以判据必须在写代码之前谈定，不能等实现完再"看着补"。

## 二、功能开关（§9 第 15 条前置，实施计划 D14）

| # | 用例 | 判定 | 证据 |
| --- | --- | --- | --- |
| F-01 | `FEATURE_COMMUNITY=false` 时所有社区接口返回 404 | 发帖/列表/详情/投票/经历/举报/申诉 逐个断言 404，**且不泄漏接口存在**（错误体与真 404 一致） | pytest |

## 三、投票规则（§11.2、§9 第 16 条）

| # | 用例 | 判定 |
| --- | --- | --- |
| V-01 | 一人一帖一票 | A 对帖 P 投「建议去」→ 余额态查票数 +1；A 再投「不建议去」→ 票数不变、只改选择 |
| V-02 | 改票不增加人数 | 改票后「投票人数」不 +1，只有「建议/不建议」两个计数互换 |
| V-03 | 发帖人不能给自己投票 | 发帖人投自己的帖子 → 403/422，且票数不变 |
| V-04 | 新注册未满 24h 不能投票 | 注册 0 小时的账号投票 → 拒绝（403 或 422），错误码可判别 |
| V-05 | 新注册未满 24h 不能发帖 | 同上 |
| V-06 | 新注册未满 24h 不能写经历 | 同上 |
| V-07 | 满 24h 后恢复权限 | 把 created_at 改到 25 小时前 → 投票/发帖成功 |
| V-08 | 未登录不能投票 | 401 |
| V-09 | 并发重复投票只算一票 | 同账号并发 5 次投同一帖 → 最终只有 1 票（唯一约束生效） |
| V-10 | 投票选项目只能二选一 | 传第三值 → 400 |

**数据结构断言**：`votes` 表必须存在 `unique(post_id, user_id)` 约束（直接查 schema 或制造重复插入验证）。

## 四、内容风控三道（§11.3、§9 第 17 条）

### 4.1 敏感词测试集 v1（先出词表与用例）

| 类别 | 样例（测试用） | 期望处理 |
| --- | --- | --- |
| 辱骂/人身攻击 | 「傻X」「去死」「垃圾人」 | **拦截** |
| 定性别名（对企业/个人） | 「骗子公司」「黑心企业」「骗子」「无良公司」 | **提示改写**（不直接拦截，要求改成事实描述后才能提交） |
| 色情暴力 | 敏感词库典型样例 | 拦截 |
| 违法有害 | 「兼职刷单」「代开发票」等 | 拦截 |
| 手机号 | `13812345678` | 打码 `138****5678` |
| 微信号 | `wxid_abc123`、`加V：xxx` | 打码 |
| QQ 号 | `123456789` | 打码 |
| 身份证号 | `110101199003074415` | 打码 |
| 银行卡号 | `6222021234567890123` | 打码 |
| 人名 | 「张经理」「李女士」 | 打码 |
| 门牌号 | 「人民路 22 号 3 单元 501」 | 打码/去地名细节 |

> **词表落地**：`tests/community/sensitive_words_v1.json`，每条含 `类别 / 输入 / 期望动作(block|rewrite|mask) / 说明`。
> 运营可以在 `sensitive_words` 表增删词；测试用**固定词表**做回归，避免运营改词导致测试漂移。

| # | 用例 | 判定 |
| --- | --- | --- |
| S-01 | 拦截类词一律拒绝发布 | 逐条投喂，全部被拒，错误码可判别 |
| S-02 | 定性词返回「提示改写」而非直接拒绝 | 返回明确提示 + 可改写的定位（哪几个字），用户改完能提交 |
| S-03 | 改写后能提交 | 把定性词改成事实描述 → 发布成功 |
| S-04 | 打码在**发布前**完成 | 帖子里存的图片/文本是打码后的；库里不落原文（查库验证） |
| S-05 | 后台可增删敏感词 | 管理员接口增词 → 立刻生效（不发版） |
| S-06 | 图片走内容安全 | 违规图片被拒 |
| S-07 | 先审后发 | 机器审核通过即发布；「拿不准」的进人工审核状态，不对其他人可见 |

## 五、治理流程（§11.3 事后）

| # | 用例 | 判定 |
| --- | --- | --- |
| R-01 | 举报满 3 次自动隐藏 | 3 个不同账号举报同一帖 → 状态变 hidden，其他人看不到 |
| R-02 | 隐藏阈值可配置 | 改配置为 5 → 3 次不隐藏，5 次隐藏 |
| R-03 | 同一账号重复举报只算一次 | 1 个账号报 5 次 → 不触发隐藏 |
| R-04 | 企业申诉 24h 目标 | 申诉记录含 `expect_reply_within_hours=24`；处理结果三选一（保留/修改/删除） |
| R-05 | 申诉结果通知发帖人 | 断言通知记录生成 |
| R-06 | 处理记录长期保存 | 申诉/举报处理记录不随帖子删除而删 |
| R-07 | 违规账号禁言/封号 | 多次违规 → 状态变更，且其内容不可再发 |

## 八、验收第 15 条：全流程端到端

```
1. 用户 A 上传截图 → 得到检查记录 → 发起求助（关联 report_id）
2. 断言：自动打码已生效；提问 ≤200 字；勾选「真实经历」；匿名发布
3. 机器审核通过 → 帖子可见
4. 用户 B 投票「不建议去」+ 选理由标签「我也被要求过交钱」
5. B 改票为「建议去」→ 断言票数正确变化、人数不变
6. 用户 C 写经历
7. 用户 D 举报 → 断言记录
8. 企业侧提交申诉 → 断言进入处理队列
9. 管理员处理申诉 → 断言结果通知到发帖人
```

## 十、新增数据表断言（§11.4）

六张表必须存在且字段齐全：

| 表 | 关键约束 |
| --- | --- |
| `posts` | 含 `report_id`（关联检查记录）、`status`（审核中/已发布/已隐藏/已删除） |
| `votes` | **`unique(post_id, user_id)`**（一人一票）、理由标签字段 |
| `experiences` | `useful_count`（有用数） |
| `reports` | 对象类型 + 对象 id + 举报人 + 处理结果 |
| `appeals` | 企业名 + 认证材料 + 处理结果 + 处理人 |
| `sensitive_words` | 词 + 级别（拦截/提示改写） |

**额外断言**：
- 所有表**不存用户截图原图**（只存打码后地址）
- SQLite DDL 与 `backend/sql/` 下的 MySQL 版 DDL **字段一致**（防两套漂移）
