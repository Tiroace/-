### 2.1 推演过程（可复核）

```
① 数据库标记到期       : 22h
② 本地磁盘文件被删     : 22h ~ 23h   （到期后最多等一个 1 小时的扫描周期）
③ OSS 对象被删         : 不适用（D37：截图不进 OSS）
```

```python

print(local_min, local_max)    # 22 23  -> 删除 <=23h，24 小时承诺成立
```

## 3. 为什么 OSS 做不到「精确 24 小时」（附官方原文）

阿里云 OSS 生命周期规则的删除时间参数**最小单位是天**（`Days`），没有「小时」粒度。
官方文档《[基于最后一次修改时间的生命周期规则](https://help.aliyun.com/zh/oss/user-guide/lifecycle-rules-based-on-the-last-modified-time)》原文两条关键规则：

> ①「如果生命周期规则指定的时间策略是按指定天数（**Days**），则 Object 的最后修改时间与**规则开始执行时间（8:00）**必须**间隔 24 小时以上**。」

> ②「规则生效后，华东1（杭州）、华东2（上海）……地域，执行 Object 数在 10 亿以内的生命周期相关操作（包括 Object 删除……）**通常情况下在 24 小时内完成**；……如出现以下情况，则**可能使任务执行时间超过 24 小时，甚至持续数天到数周**：扫描 Object 数过多、待执行生命周期的 Object 数过多……」

**把这两条合起来看，删掉一个对象的真实窗口是：**

```
上传时刻 T
  ↓  规则在每天 08:00 执行
下一个 08:00 若距 T 不足 24h → 跳过（不满足规则①）
  ↓
次日 08:00 才轮到它 → 此时距 T 约 24~48h
  ↓  执行任务本身可能再花最多 24h（规则②）
实际删除时刻 ≈ T + 24h ~ T + 72h（正常 24~48h，极端情况更久）
```

**修正上文第 2 节的结论**：我在写第 2 节时按「24–48 小时」估算是**偏乐观**的。
按官方规则，**最坏情况可以达到 72 小时**（排队 + 执行时长）。
不过本项目截图量极小（每天几十到几百张，远低于 10 亿），规则②「超过 24 小时」的极端条件不适用，
**实际可以按 24–48 小时规划**，但**对外承诺不能按「24 小时内」写**。

- 同类产品（腾讯云 COS 等）也是天粒度 → **换厂商解决不了**。
- 唯一能做到「精确 N 小时」的办法是**自己对账式清理**：写定时任务主动调 DeleteObject 删除超过 N 小时的对象。
  代价：要写代码、要保证任务不漏跑、多一层失败风险。OSS 规则仍建议留作最后防线。

## 4. 现有文案与事实的差距

| 位置 | 现在写的 | 与事实的差距 |
| --- | --- | --- |
| 隐私政策草稿 §二 | 「分析完成后 **24 小时内删除原图**」 | ①本地文件满足（23–24h）；③OSS 对象**不满足**（24–48h） |
| 隐私政策草稿 §五 | 「对象存储生命周期规则自动删除，**并有删除记录可查**」 | 「自动删除」成立；「删除记录可查」——`deletion.log` 只记本地文件删除，**OSS 生命周期删除不写我们的日志**，这半句目前没有证据支撑 |

> 第 2 行是我核出来的**额外问题**：不是措辞松紧，是「有删除记录可查」这句**目前是空的**——
> OSS 生命周期删除由云厂商执行，不会回调我们的 `deletion.log`。
> 要兑现这句，得上 OSS 事件通知（调 `deletion.log` 或 SLS），属于新增开发工作。

## 6. 「删除记录可查」这半句怎么办

隐私政策 §五 写了「并有删除记录可查」，但目前 `deletion.log` 只覆盖本地文件删除。
三个选择：

| 选择 | 做法 | 需要谁 |
| --- | --- | --- |
| E1 | OSS 配置事件通知（ObjectDeleted），日志投递到 SLS | 运维配置，部署时做 |
| E2 | 删掉「有删除记录可查」半句，只写「自动删除」 | 产品改文案 |
| E3 | 保留，但明确指「本地文件的删除记录」 | 产品改文案 |

**运维能做 E1**，但要等服务器和 OSS 到位；在那之前这句在技术上不成立。
