### 1.1 OSS 截图对象生命周期规则：24 小时自动删除

**为什么单独列**：代码里 `QBL_UPLOAD_TTL_HOURS` 只是数据库字段（`backend/app/routers/analysis.py:137`），**它不删 OSS 上的对象**。OSS 对象要靠 Bucket 生命周期规则删，这条规则只能在控制台/命令行配置，代码管不到。

| # | 检查项 | 通过标准 | 证据 | 勾 |
| --- | --- | --- | --- | --- |
| 1.1.1 | Bucket 存在且**私有读** | ACL = private，未开公共读 | OSS 控制台 Bucket 概览截图 `reports/ops/oss-bucket-acl.png` | ☐ |
| 1.1.2 | 生命周期规则存在 | 规则名 `shots-24h`，前缀 `shots/`，**删除时间 = 对象创建后 24 小时** | `ossutil lifecycle get oss://<bucket>` 输出 → `reports/ops/oss-lifecycle.txt` | ☐ |
| 1.1.3 | 分片清理规则存在 | `abort-incomplete-multipart-upload` = 7 天 | 同上输出里含该规则 | ☐ |
| 1.1.4 | **未开启版本控制** | Bucket 版本控制 = 未开启 | 关版本控制的原因：开了之后「删除」只是加删除标记，对象实际还在，24 小时删除**当场失效** | 控制台截图 + 说明 | ☐ |
| 1.1.5 | **实测对象会被删** | 传一个测试对象到 `shots/test/`，**次日**复查已不存在 | 两次 `ossutil ls oss://<bucket>/shots/test/` 输出对比 → `reports/ops/oss-ttl-proof.txt` | ☐ |
| 1.1.6 | 生命周期规则**导出留档** | 规则 JSON 导出文件在仓库 `ops/evidence/` 下 | 文件路径 | ☐ |

**配置命令（阿里云 ossutil 示例，上线时执行）**：

```bash
# 规则文件 lifecycle.xml
cat > lifecycle.xml <<'XML'
<LifecycleConfiguration>
  <Rule>
    <ID>shots-24h</ID>
    <Prefix>shots/</Prefix>
    <Status>Enabled</Status>
    <Expiration><Days>1</Days></Expiration>
  </Rule>
  <Rule>
    <ID>abort-multipart-7d</ID>
    <Prefix>shots/</Prefix>
    <Status>Enabled</Status>
    <AbortMultipartUpload>
      <DaysAfterInitiation>7</DaysAfterInitiation>
    </AbortMultipartUpload>
  </Rule>
</LifecycleConfiguration>
XML

ossutil lifecycle set lifecycle.xml oss://<bucket>
ossutil lifecycle get oss://<bucket> > ops/evidence/oss-lifecycle.txt   # ← 证据
```

> ⚠️ **`Days: 1` 是「按天粒度」，意味着实际删除发生在对象创建后 24–48 小时之间**（OSS 按天扫描）。
> **但 D37 已定：一期截图不落 OSS**，走容器本地盘 + 应用层每小时清理（TTL 22h ⇒ 删除 ≤23h）。
> 因此本节整体**改为「将来若改用对象存储时」的参考**，现行方案见 [`云托管部署手册.md`](云托管部署手册.md) §5。
> 保留原因：一旦将来要加对象存储，这里的规则与坑仍然成立。

### 1.2 `var/log` 挂持久卷：容器重建不丢日志

**为什么单独列**：`backend/app/logging_setup.py` 把日志写到 `project_root/var/log/app.log`，`backend/app/retention.py` 把截图删除日志写到 `var/log/deletion.log`。容器内 `project_root=/app`，所以路径是 **`/app/var/log`**。原 compose 只挂了 `/data`，**容器一重建这两个日志就全丢**，R-04「留存 6 个月」当场不成立。

**已修复**：`ops/docker-compose.yml` 的 api 服务新增 `api_logs:/app/var/log`，并声明 `api_logs` 卷。

| # | 检查项 | 通过标准 | 证据 | 勾 |
| --- | --- | --- | --- | --- |

| 1.2.2 | 容器内日志目录是挂载点 | `docker inspect <api容器>` 的 Mounts 里有 `/app/var/log` | `docker inspect ... > reports/ops/api-mounts.json` | ☐ |

| 1.2.4 | **重建容器后日志还在**（关键） | `docker compose up -d --force-recreate api` 后 `/app/var/log` 历史文件仍在 | 重建前后 `ls -l` 对比 → `reports/ops/log-persist-proof.txt` | ☐ |

### 1.3 SLS 日志保留 ≥180 天（含截图删除日志）

**为什么单独列**：《网络安全法》第二十一条要求网络日志留存不少于六个月。容器日志只是本地兜底，真正满足留存要求的是 SLS。**「SLS 建了但保留期是默认 30 天」等于没达标**，必须显式查。

| # | 检查项 | 通过标准 | 证据 | 勾 |
| --- | --- | --- | --- | --- |
| 1.3.1 | Project / Logstore 已建 | Project `qbl-prod`，Logstore `app`、`access`、`deletion` | 控制台截图 | ☐ |
| 1.3.2 | **保留期 ≥180 天**（关键） | 三个 Logstore 的 `ttl` 都是 **190**（与代码 `RETENTION_DAYS` 对齐，留 6 个日历月余量） | `aliyun log get_logstore --project ... --logstore ...` 输出 | ☐ |
| 1.3.3 | Nginx 访问日志已采集 | Logtail 配好，能查到最近 1 小时的访问记录 | 查询截图 | ☐ |
| 1.3.4 | 应用日志 `app.log` 已采集 | 同上 | 查询截图 | ☐ |
| 1.3.5 | **截图删除日志已采集**（新增要求） | `deletion.log` 进 SLS `deletion` Logstore，能按时间查到「删了哪个 image_id」 | 查询截图 | ☐ |
| 1.3.6 | MySQL 慢查询/错误日志已采集 | 同上 | 查询截图 | ☐ |
| 1.3.7 | 日志里无 PII | 抽 10 条看，无完整手机号、无截图原文 | 抽样记录 | ☐ |
| 1.3.8 | 保留期配置导出留档 | 配置 JSON 存 `ops/evidence/sls-retention.json` | 文件路径 | ☐ |

> **保留期为什么是 190 不是 180**：180 个按天轮转备份 ≈ 覆盖 181 天（当天 + 180 份历史），而「6 个月」在 2 月/7 月等是 181–184 天，180 不严格够。190 留余量。开发者侧 `logging_setup.py` 的 `RETENTION_DAYS` 也同步改到 190，两侧口径必须一致。
