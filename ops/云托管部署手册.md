# 微信云托管部署手册（D38 个人主体路线）

> 负责人：运维｜更新：2026-11-03
> 前提：老板已开通云托管环境（个人主体小程序即可）
> 评估结论与依据见 [`微信云托管评估.md`](微信云托管评估.md)

---

## 0. 一句话

把 `ops/Dockerfile.cloudrun` 复制成项目根目录的 `Dockerfile`，整个项目文件夹上传到云托管控制台，点发布。
**不需要域名、不需要域名备案、不需要买服务器。**

---

## 1. 部署前检查（5 分钟）

| # | 检查 | 命令/动作 |
| --- | --- | --- |
| 1 | 云托管环境已创建 | 云托管控制台 → 能看到环境 ID |
| 2 | 服务已新建，名如 `qbl-api` | 「允许公网访问」**建议关闭**（小程序用 callcontainer 走内网，更安全） |
| 3 | 容器规格已选 | 见 §3，建议 **2 核 4G** 起步 |
| 4 | 日志采集路径已配 | 服务设置 → 日志采集路径：`/app/var/log` 或留空取 stdout |
| 5 | Dockerfile 在根目录 | `cp ops/Dockerfile.cloudrun Dockerfile` |

---

## 2. 部署步骤

### 2.1 准备代码包

```bash
# 在项目根目录
cp ops/Dockerfile.cloudrun Dockerfile

# 确认关键目录都在（缺一个就起不来）
ls Dockerfile requirements.txt engine/ rules/ backend/
```

> ⚠️ **不要**把 `.env`、`var/`、`data/testset/real_images/` 打进代码包（体积大且含敏感内容）。
> 上传前确认 `var/` 已被 `.gitignore` 忽略；手动上传文件夹时会一并带上，建议先清理 `var/`。

### 2.2 上传与发布

1. 云托管控制台 → 服务 → 「部署发布」
2. 选择方式：**手动上传代码包** → 上传方式：**文件夹**
3. 选中**项目根目录**（就是含 `Dockerfile` 的那一层）
4. 点「发布」，等构建（首次约 5–10 分钟，装 OCR 依赖比较久）
5. 看构建日志，出现 `Application startup complete` 即成功

### 2.3 验证

```bash
# 用控制台给的公网域名（若开了公网访问）
curl https://<服务默认域名>/health
# 期望：{"ok":true,"data":{"status":"up","service":"qbl-backend","version":"0.1.0"}}
```

## 3. 容器规格怎么选

| 规格 | 适用 | 月费（1 副本常驻） | OCR 表现 |
| --- | --- | --- | --- |
| 1 核 2G | ❌ 不建议 | 85.68 元 | 预计 >10 秒 |
| **2 核 4G** | **内测期起步** | **171.36 元** | 预计 6–8 秒 |
| 4 核 8G | 上线候选 | 342.72 元 | 预计 3–5 秒 |
| 8 核 16G | 上限 | 约 685 元 | 预计能达标 |

**扩容策略**：
- 内测期：最小副本 **0**（无流量不花钱），能接受冷启动慢
- 上线期：最小副本 **1**（避免冷启动拖慢「30 秒出报告」）
- 自动扩容：CPU 使用率 >70% 触发

> 规格与月费来源见 `微信云托管评估.md` §3。

## 4. 数据与存储（⚠️ 最容易踩的坑）

云托管的**容器本地盘不持久**：实例缩容到 0、滚动发布时，本地文件全部消失。

| 数据 | 放哪 | 注意 |
| --- | --- | --- |
| 截图 | 容器本地 `/app/var/uploads` | 丢了正好（D37：本来就 24 小时删） |
| **数据库** | **必须外部化** | 选项：① 云托管自带 MySQL（0.342 元/个·小时）；② 用容器内 SQLite → **实例重建就丢全部用户数据，不可接受** |
| 日志 | `/app/var/log` + 采集到云托管服务日志 | 本地盘会丢，必须靠采集 |
| 规则库 | 镜像内 `rules/` | 随镜像，安全 |

**结论：上线前必须接 MySQL（云托管自带或外部）**，否则用户数据保不住。

## 5. 定时清理（截图 24 小时内删除）

代码里已有 `backend/app/retention.py`，启动时自动拉起后台线程，每小时扫一次。
云托管下要注意：

- 实例缩放到 0 时不跑定时任务 → **下次冷启动后才会清理**。
- TTL 22h + 每小时扫 ⇒ 单实例场景下删除 ≤23h（D37 定案）。
- **但若长时间无请求导致实例缩容到 0，清理会暂停**，直到下一次有请求唤醒实例。
- **缓解**：配置云托管「定时触发」（官方支持定时访问 URL），每小时打一次 `/health`，保证实例不被缩到 0。

> 这条要写进上线验收：**验证实例缩容到 0 后，清理是否仍能按承诺执行**。

## 6. 环境变量（在云托管控制台配置，不写进代码）

| 变量 | 说明 |
| --- | --- |
| `QBL_ENV` | `prod` |
| `QBL_USE_LLM` | `0`（一期禁止大模型） |
| `QBL_FEATURE_COMMUNITY` | `0`（社区关闭） |
| `QBL_UPLOAD_TTL_HOURS` | `22`（D37 定案） |
| `QBL_WORKER_THREADS` | 2–4 |
| `QBL_ADMIN_TOKEN` / `QBL_TOKEN_SECRET` / `QBL_PAY_SECRET` | 随机强口令，**在控制台配置** |
| `QBL_WX_APPID` / `QBL_WX_SECRET` | 正式 AppID 后填 |

## 7. 更新发布

- 改代码后重新上传代码包发布，或绑定 Git 仓库走流水线。
- 支持灰度：发布单里设流量比例，出问题点「回退」。
- **发布前必须过测试**：`python -m pytest -m smoke`。

## 8. 已知限制（说白了）

1. **OCR 慢**：真实截图（1290×2796，34 行文字）本机实测 **12–35 秒**，且本机 CPU 满载、数据波动大。
   **「单张 ≤4 秒」达不到**。完整依据与优化/降级方案见 [`OCR性能缺口-优化与降级方案.md`](OCR性能缺口-优化与降级方案.md)。
2. **本地盘不持久**：数据库必须外部化，**SQLite 会随容器重建丢数据**。
3. **缩容到 0 时定时任务不跑**：靠定时触发保活。
4. **没有固定出口 IP**（除非买 49 元/月增值服务）：若有外部接口要求白名单，需另外处理。

## 9. 部署当天流程（AppID 到手后照做）

> 目标：**AppID 到手当天部署完**。总耗时约 60–90 分钟，其中构建占大头。
> 配置选项见 [`云托管-配置选定清单.md`](云托管-配置选定清单.md)。

### 9.1 时间线

| 时刻 | 动作 | 负责人 | 产出 |
| --- | --- | --- | --- |
| T+0 | 确认 AppID 已到手、老板已开通云托管 | 个人助理 | 环境 ID |
| T+5min | 生成部署包 P1，本地自检 | 运维 | `ops/dist/qbl-cloudrun-*/` 0.49MB |
| T+10min | 建服务、选规格、配副本、配日志、填环境变量（P2–P6） | 运维 | 服务就绪 |
| T+20min | 上传发布（P7），等构建 | 运维 | 构建日志 |
| T+40min | 构建完成，健康检查（P8） | 运维 | `/health` 200 |
| T+45min | **OCR 实测基线（P9）**——最关键的一步 | 运维 + 开发者 | 真实耗时数字 |
| T+60min | 清理任务与容器重建验证（P10/P11） | 运维 | 确认数据策略 |
| T+70min | 小程序端联调（callContainer 通不通） | 前端 + 运维 | 真机页面能出报告 |
| T+90min | 记录部署结果，更新 STATUS | 运维 | 群内回报 |

### 9.2 关键检查点（过不了就停下，不许往下走）

| 检查点 | 通过标准 | 不过怎么办 |
| --- | --- | --- |
| CP1 构建成功 | 日志有 `Application startup complete` | 看构建日志，常见是 OCR 依赖装不上 → 回滚到无 OCR 镜像先跑通 |
| CP2 健康检查 | `/health` 返回 `ok:true` | 查环境变量是否缺失 |
| CP3 **OCR 真实耗时** | 记录数字，**与产品确认验收线** | 若远超 10 秒，暂停并升级到 Chief |
| CP4 数据不丢 | 容器重建后数据库仍在 | **若用 SQLite 则必然丢** → 立即切 MySQL 或明确告知内测数据不保留 |
| CP5 小程序调用通 | 真机能出报告 | 查 `X-WX-SERVICE` 与基础库版本 ≥2.23.0 |

## 10. 回滚方案

### 10.1 三种回滚层级

| 场景 | 动作 | 耗时 | 数据影响 |
| --- | --- | --- | --- |
| **代码问题**（新版本报错） | 控制台 → 部署发布 → 历史版本 → 选上一版 → 发布 | 约 3 分钟 | 无 |
| **配置问题**（规格/环境变量错） | 服务设置改回正确值 → 重新发布（会生成新版本） | 约 5 分钟 | 无 |
| **数据问题**（误删/损坏） | 只能用备份。**云托管不自动备份 SQLite**；MySQL 版需在云上做备份 | 10–30 分钟 | 视备份点 |

### 10.2 回滚判定（出现任一条立即回滚）

- `/health` 连续 3 次不通
- 小程序调用持续 5xx
- 报错率 > 5%
- 出现数据写入异常

### 10.3 回滚后必做

1. 群内说明：**哪条没过、回滚到哪个版本、下次重试计划**。不许不吭声。
2. 在 `docs/STATUS.md` 记一笔。
3. **不许「带着问题上线明天再修」。**

### 10.4 灰度发布（推荐）

云托管支持流量比例灰度：
1. 发布新版本时勾选灰度，初始流量 0%
2. 拉 1–2 个人（openid 白名单）先试
3. 无问题调到 10% → 50% → 100%
4. 中途出问题点「回退」，流量全切回旧版本

> **首次部署没得灰度**（还没有旧版本），首次必须一次到位，所以要严格走 §9.2 检查点。
