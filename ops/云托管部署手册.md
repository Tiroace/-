## 0. 一句话

把 `ops/Dockerfile.cloudrun` 复制成项目根目录的 `Dockerfile`，整个项目文件夹上传到云托管控制台，点发布。
**不需要域名、不需要域名备案、不需要买服务器。**

## 2. 部署步骤

### 2.1 准备代码包

```bash
# 在项目根目录
cp ops/Dockerfile.cloudrun Dockerfile

# 确认关键目录都在（缺一个就起不来）
ls Dockerfile requirements.txt engine/ rules/ backend/
```

> ⚠️ **不要**把 `.env`、`var/`、`data/testset/real_images/` 打进代码包（体积大且含敏感内容）。
> 上传前确认 `var/` 已被 `.gitignore` 忽略；手动上传文件夹时会一并带上，建议先清理 `var/`。

### 2.2 上传与发布

1. 云托管控制台 → 服务 → 「部署发布」
2. 选择方式：**手动上传代码包** → 上传方式：**文件夹**
3. 选中**项目根目录**（就是含 `Dockerfile` 的那一层）
4. 点「发布」，等构建（首次约 5–10 分钟，装 OCR 依赖比较久）
5. 看构建日志，出现 `Application startup complete` 即成功

### 2.3 验证

```bash
# 用控制台给的公网域名（若开了公网访问）
curl https://<服务默认域名>/health
# 期望：{"ok":true,"data":{"status":"up","service":"qbl-backend","version":"0.1.0"}}
```

## 3.1 副本策略：最小副本 0 + 定时扩容（**替代原「最小 1 常驻」方案**）

### 为什么改

原方案建议「最小副本 1」，是为了避免冷启动。但个人助理 2026-11-03 核对了官方免费额度原文：

> 「首个环境系统会赠送一定免费额度供开发者使用，**该免费额度有效期为 3 个月**」——CPU 720 核·小时、内存 1440 GB·小时。
> 来源：[产品定价](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/Billing/price.html)

**1 核 2G 常驻一个月 = 1×720 = 720 核·小时 + 2×720 = 1440 GB·小时，正好把 3 个月的额度一个月吃光。**
所以「常驻」在前 30 天免费，**第 31–90 天要付 171.36 元**。

> ⚠️ 个人助理原话「1 核 2G 常驻跑满一个月正好卡在额度内 = 0 元」——**第一句对、结论不完整**：
> 一个月确实免费，但那消耗的是**3 个月的全部额度**，后面两个月要照付。完整复核见
> [`云托管上线操作单-老板照着点.md`](云托管上线操作单-老板照着点.md) §5.2。

### 怎么配

| 配置项 | 值 | 说明 |
| --- | --- | --- |
| **实例副本数 最小值** | **0** | ⚠️ 关键：设 0 才能无流量不计费 |
| 实例副本数 最大值 | **1** | 1 核 2G 跑 OCR，多副本会互相抢核，**不要放开** |
| 扩容触发 | CPU 使用率 > 70% | 最多扩到 1，不会多花钱 |
| **定时扩缩容** | 每日 **08:00 扩到 1 副本 / 23:00 缩回** | 白天用户不用等冷启动 |
| 定时规则数量 | 1 个（官方最多支持 3 个时段） | 够用 |

**官方原文依据**（[服务设置](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/guide/service/pipeline.html)）：
> 「如服务需要低成本，无流量时无成本，可将实例副本数最小值设为=0；当该服务 **30min 内无流量**则后台会将实例副本数缩容为 0」
> 「支持服务定时扩缩容……支持每日/每周/每月/不重复等四种定时类型」
> 「定时扩容实例副本数不能设置小于最小实例副本数且**不可设置为 0**」

> ⚠️ 注意最后一句：定时规则**不能把副本设成 0**，所以「缩回」靠的是「最小副本 = 0 + 30 分钟无流量自动缩容」，
> 不需要也无法写一条「23:00 缩到 0」的规则。

**路径**：云托管控制台 → 服务 → 服务设置 → 基础信息 → 实例副本数 → 最小值填 **0**、最大值填 **1**。

### 费用

| 副本策略 | 前 30 天 | 第 31–90 天 | 3 个月合计 | 之后每月 |
| --- | --- | --- | --- | --- |
| 常驻（原方案，最小 1） | 0 元 | **171.36 元** | 约 171 元 | **85.68 元** |
| **定时扩容（现方案）** | 0 元 | **107.10 元** | **约 107 元** | **53.55 元** |
| 全按量缩容 | 0 元 | 约 10–40 元（估算） | 约 10–40 元 | 约 5–20 元 |

> 定时扩容按「08:00–23:00 共 15 小时/天 × 60 天 × 0.119 元/时」算：
> `0.055×1 + 0.032×2 = 0.119 元/时`，`0.119 × 15 × 60 = 107.10 元`。
> 全按量是估算区间，**不是官方数字**，以「费用中心-账单」为准。

### 冷启动到底多慢

**目前没有实测数据 → 待核实。**
官方只说「再次冷启动时可能有服务延迟，具体延迟时间由服务启动速度决定」。
我们的镜像要加载 OCR 模型（约 300MB），启动时间可能不短。
**部署当天触发一次缩容→唤醒，实测这个延迟**，记进 §9 检查点 CP3。

**降冷启动的三件事（已具备，无需改代码）**：
1. 生产环境启动时会**预热 OCR 模型**（`backend/app/main.py:143`，`is_production` 时自动开）；
2. 官方支持**定时扩缩容**，白天保持 1 副本；
3. 官方**定时触发**可每小时打一次 `/health` 保活（见 §5）。

## 3.2 自动扩容的坑

- 官方限制：**实例数最大值 > 50 需工单**，我们远用不到。
- 扩容是按 **CPU/内存使用率**触发的，OCR 是 CPU 密集型，高峰时会快速扩容。
- **但 3 张图并行处理如果在一个实例里排队**，扩不出实例也没用——
  这要求后端用**线程池或独立 worker** 真并发，不是靠云托管扩容解决。
  （D40 明确「3 张禁止串行」，这条是开发者的活，运维只负责把实例数留够。）

## 4. 数据与存储（⚠️ 最容易踩的坑）

云托管的**容器本地盘不持久**：实例缩容到 0、滚动发布时，本地文件全部消失。

| 数据 | 放哪 | 注意 |
| --- | --- | --- |
| 截图 | 容器本地 `/app/var/uploads` | 丢了正好（D37：本来就 24 小时删） |
| **数据库** | ⚠️ **当前仍是容器内 SQLite**（定档决定不开 MySQL） | **实例重建/发布就丢全部用户数据**，见 §11.2 |
| 日志 | 容器本地 `/app/var/log` + 云托管服务日志采集 | 本地盘会丢，必须靠采集 |
| 规则库 | 镜像内 `rules/` | 随镜像，安全 |

### 4.1 定档结论：内测期不开 MySQL

个人助理 2026-11-03 定档：**不买云托管自带 MySQL**（0.342 元/小时 = **246 元/月**，比容器还贵），
数据先用容器内 SQLite（D2）。对象存储也不开（截图 24 小时必删，不落存储）。

### 4.2 ⚠️ 数据会丢（已定：接受，0 元）

> ## 🚨 部署前必读：**内测期数据会丢，这不是 bug**
>
> **个人助理 2026-11-03 已代老板拍板：不买云托管 MySQL，内测期接受数据丢失。**
>
> 用户会看到的现象（**提前告诉测试人员，别当故障排查**）：
> - 小程序**重启/发布新版本后，免费扫描次数被重置**；
> - **检查历史记录消失**，报告列表清空；
> - 前一天在、第二天不见了。
>
> **以上全部是预期行为，不是程序错误，不要提缺陷单。**

**技术事实**（不是推测）：

1. 官方原文：「30min 内无流量则后台会将实例副本数缩容为 0」（[服务设置](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/guide/service/pipeline.html)）；
2. 我们的副本策略是**最小 0**（§3.1），所以**夜里必然缩容到 0**；
3. 缩容 = 实例销毁，容器内 `/app/var/backend/qbl.db` 随之消失；
4. 当前数据库是 **SQLite 单文件 + WAL 模式**（`backend/app/config.py:41`、`backend/app/db.py:302`），
   WAL 还会产生 `-wal`/`-shm` 两个伴随文件，**即使挂共享盘也不能多副本并发写**。

**后果**：只要实例被销毁一次（扩缩容、发布新版本、平台重建），**所有用户记录清零**。

**决定与执行口径（已定，不再待议）**：

| 方案 | 状态 | 代价 | 数据后果 |
| --- | --- | --- | --- |
| **A. 内测期接受丢数据** | ✅ **已定，当前执行** | **0 元** | 每次重建清零，**内测数据不当正式资产** |
| B. 开云托管 MySQL | ⏸ 暂不做（等有真实用户留存需求再上） | 246 元/月 + 开发者改 `db.py` | 数据保住 |
| C. 外部 MySQL | ⏸ 不采用 | 价格待核实 + 开发者改 `db.py` | 数据保住 |

> **个人助理 2026-11-03 的判断（运维认同）**：246 元/月不值得为内测花；
> 15 个内测用户丢记录不影响验证产品；真运营需要持久化时再上 MySQL，那时开发改 `db.py` 也有真实数据量参考。
>
> **运维执行要求**：
> 1. 部署回报里**必须写明「内测数据会丢」**，不许含糊；
> 2. 把上面 🚨 那段**原样转给软件测试者/前端/开发者**，避免有人把「次数重置」当 bug 追杀；
> 3. 正式对外（要留用户口碑/反馈）之前**必须**先切 MySQL。

## 5. 定时清理（截图 24 小时内删除）

代码里已有 `backend/app/retention.py`，启动时自动拉起后台线程，每小时扫一次。
云托管下要注意：

- 实例缩放到 0 时不跑定时任务 → **下次冷启动后才会清理**。
- TTL 22h + 每小时扫 ⇒ 单实例场景下删除 ≤23h（D37 定案）。
- **但若长时间无请求导致实例缩容到 0，清理会暂停**，直到下一次有请求唤醒实例。
- **缓解**：配置云托管「定时触发」（官方支持定时访问 URL），每小时打一次 `/health`，保证实例不被缩到 0。

> 这条要写进上线验收：**验证实例缩容到 0 后，清理是否仍能按承诺执行**。

## 6. 环境变量（在云托管控制台配置，不写进代码）

> ⚠️ **生产环境带默认口令会拒绝启动**：`backend/app/main.py:125` 启动第一件事调
> `assert_production_ready()`，`QBL_ENV=prod` 时三个密钥任一为空或用默认值，服务直接起不来
> （`backend/app/config.py:126`）。**所以下面标红的三项一次都不能错。**

| 变量 | 值 | 说明 |
| --- | --- | --- |
| `QBL_ENV` | `prod` | 生产标识；同时启用 OCR 预热与「默认口令拒启」 |
| `QBL_USE_LLM` | `0` | 一期禁止大模型（D19） |
| `QBL_FEATURE_COMMUNITY` | `0` | 社区关闭（D14） |
| `QBL_UPLOAD_TTL_HOURS` | `22` | D37 定案：22h + 每小时扫描 ⇒ 删除 ≤23h |
| **`QBL_WORKER_THREADS`** | **`1`** | **1 核 2G 定档：开 2 个线程会互相抢核，反而更慢**（原手册写 2–4 是 4 核时代的数） |
| `QBL_OCR_WARMUP` | `1` | `QBL_ENV=prod` 已自动开，写 1 是双保险（`main.py:143`） |
| **`QBL_ADMIN_TOKEN`** | 随机 32 位 | ⚠️ **必填**，缺了就起不来 |
| **`QBL_TOKEN_SECRET`** | 随机 32 位 | ⚠️ **必填**，缺了就起不来 |
| **`QBL_PAY_SECRET`** | 随机 32 位 | ⚠️ **必填**，缺了就起不来 |
| `QBL_WX_APPID` | `wx807821c2d1fb9f3b` | 正式 AppID（已到手） |
| `QBL_WX_SECRET` | 小程序 AppSecret | **控制台填，不发言群** |
| `QBL_DEV_MODE` | **不要设**（默认 0） | 设 1 会**直接拒启**（`config.py:137`） |

> 生成随机串：任意密码管理器，或本地 `openssl rand -base64 32`。**不要发群里、不要写进代码、不要写进文档。**
> 密钥只走「控制台手动填」这一条路，输入时不截屏、不转发。

## 8. 已知限制（说白了）

1. **OCR 慢**：真实截图（1290×2796，34 行文字）本机实测 **12–35 秒**，且本机 CPU 满载、数据波动大。
   **「单张 ≤4 秒」达不到**。1 核 2G 上预计**十几秒**。完整依据与优化/降级方案见 [`OCR性能缺口-优化与降级方案.md`](OCR性能缺口-优化与降级方案.md)。
2. **本地盘不持久**：数据库仍是容器内 SQLite，**实例重建就丢全部用户数据**（§4.2，阻断 #2，**已定：接受丢数据，0 元**）。
3. **缩容到 0 时定时任务不跑**：靠定时触发保活（§5）。
4. **只有 1 个实例**（最大副本 1）：1 核 2G 跑 OCR 时并发能力很弱，**3 张并行会明显变慢**，
   这是定档换来的省钱，验收时要按实际数字判，不能拿开发机数字顶。
5. **没有固定出口 IP**（除非买 49 元/月增值服务）：若有外部接口要求白名单，需另外处理。

## 9. 部署当天流程（AppID 到手后照做）

> 目标：**AppID 到手当天部署完**。总耗时约 60–90 分钟，其中构建占大头。
> 配置选项见 [`云托管-配置选定清单.md`](云托管-配置选定清单.md)。

### 9.1 时间线

| 时刻 | 动作 | 负责人 | 产出 |
| --- | --- | --- | --- |
| T+0 | 确认 AppID 已到手、老板已开通云托管 | 个人助理 | 环境 ID |
| T+5min | 生成部署包 P1，本地自检 | 运维 | `ops/dist/qbl-cloudrun-*/` 0.49MB |
| T+10min | 建服务、选规格、配副本、配日志、填环境变量（P2–P6） | 运维 | 服务就绪 |
| T+20min | 上传发布（P7），等构建 | 运维 | 构建日志 |
| T+40min | 构建完成，健康检查（P8） | 运维 | `/health` 200 |
| T+45min | **OCR 实测基线（P9）**——最关键的一步 | 运维 + 开发者 | 真实耗时数字 |
| T+60min | 清理任务与容器重建验证（P10/P11） | 运维 | 确认数据策略 |
| T+70min | 小程序端联调（callContainer 通不通） | 前端 + 运维 | 真机页面能出报告 |
| T+90min | 记录部署结果，更新 STATUS | 运维 | 群内回报 |

### 9.2 关键检查点（过不了就停下，不许往下走）

| 检查点 | 通过标准 | 不过怎么办 |
| --- | --- | --- |
| CP1 构建成功 | 日志有 `Application startup complete` | 看构建日志，常见是 OCR 依赖装不上 → 回滚到无 OCR 镜像先跑通 |
| CP2 健康检查 | `/health` 返回 `ok:true` | 查环境变量是否缺失 |
| CP3 **OCR 真实耗时** | 记录数字，**与产品确认验收线** | 若远超 10 秒，暂停并升级到 Chief |
| CP4 数据不丢 | 容器重建后数据库仍在 | **若用 SQLite 则必然丢** → 立即切 MySQL 或明确告知内测数据不保留 |
| CP5 小程序调用通 | 真机能出报告 | 查 `X-WX-SERVICE` 与基础库版本 ≥2.23.0 |

### 9.3 CP3 怎么做：在云托管里测 OCR 真实耗时

**这是整个部署最重要的一步**——D40 的验收线（单张 P95 ≤10s、3 张并行 P95 ≤25s）在开发机上
余量只有 **13–17%**，云托管若慢 20% 就会破线。**必须在云上实测，不能拿开发机数字顶。**

**准备图片**（容器里没有 `data/` 目录）：
1. 把 21 张真实图打包上传，放到容器可读的位置。
2. 登录云托管控制台 → 服务 → 「登录实例」开 webshell。
3. 或：把图片放进部署包的 `ops/testset/` 一起上传（体积约 7.5MB，可接受）。

**执行**：

```bash
# 容器内
cd /app
python /app/ops/scripts/ocr_baseline_21.py --dir /path/to/图片目录
```

**看结果**，与开发机基线对比：

| 指标 | 开发机基线 | D40 验收线 | 云上实测 | 判定 |
| --- | --- | --- | --- | --- |
| 单张 P50 | 7.92s | — | ____ | — |
| 单张 P95 | **8.32s** | ≤10s | ____ | ☐ |
| 3 张并行 P50 | 16.38s | — | ____ | — |
| 3 张并行 P95 | **21.73s** | ≤25s | ____ | ☐ |

**判定规则（1 核 2G 版，替代原 4 核版）**：

> 原版规则「10–13s 升 4 核 8G」是 2 核 4G 时代的判定。1 核 2G 下**单张超过 10 秒几乎是必然的**，
> 所以判定要按「内测期能不能忍 + 是否触发升级」来看，不是拿来否决部署。

| 云上单张 P95 | 动作 | 是否继续部署 |
| --- | --- | --- |
| ≤10s | ✅ 超出预期，直接继续 | 继续 |
| 10–20s | ⚠️ **内测期可接受**（个人助理已认账），**记录真实数字**，继续 | **继续** |
| 20–30s | ⚠️ 边缘：记录数字，**群内报 Chief + 个人助理**，由他们决定是否升级规格 | 报告后继续 |
| >30s | ❌ **停下来**，先报 Chief，不许硬上 | 暂停 |

**升级路径（真卡了再花钱）**：1 核 2G（85.68 元）→ 2 核 4G（171.36 元）→ 4 核 8G（342.72 元）。
改规格是控制台改配置 + 重新发布一版，约 5 分钟，**不需要改代码**。

**顺带测冷启动**（见 §3.1）：
把最小副本临时改成 0 → 等 30 分钟 → 访问一次 → 记录唤醒到返回的耗时 → **改回 0/1（按 §3.1 的定时策略）**。

## 10. 回滚方案

### 10.1 三种回滚层级

| 场景 | 动作 | 耗时 | 数据影响 |
| --- | --- | --- | --- |
| **代码问题**（新版本报错） | 控制台 → 部署发布 → 历史版本 → 选上一版 → 发布 | 约 3 分钟 | 无 |
| **配置问题**（规格/环境变量错） | 服务设置改回正确值 → 重新发布（会生成新版本） | 约 5 分钟 | 无 |
| **数据问题**（误删/损坏） | 只能用备份。**云托管不自动备份 SQLite**；MySQL 版需在云上做备份 | 10–30 分钟 | 视备份点 |

### 10.2 回滚判定（出现任一条立即回滚）

- `/health` 连续 3 次不通
- 小程序调用持续 5xx
- 报错率 > 5%
- 出现数据写入异常

### 10.3 回滚后必做

1. 群内说明：**哪条没过、回滚到哪个版本、下次重试计划**。不许不吭声。
2. 在 `docs/STATUS.md` 记一笔。
3. **不许「带着问题上线明天再修」。**

### 10.4 灰度发布（推荐）

云托管支持流量比例灰度：
1. 发布新版本时勾选灰度，初始流量 0%
2. 拉 1–2 个人（openid 白名单）先试
3. 无问题调到 10% → 50% → 100%
4. 中途出问题点「回退」，流量全切回旧版本

> **首次部署没得灰度**（还没有旧版本），首次必须一次到位，所以要严格走 §9.2 检查点。

## 11. 两处部署阻断的修复与本次配置（个人助理要求写进本文）

> 背景：个人助理 2026-11-03 转达「把那两处部署阻断的修复和本次配置写进部署手册」。
> 下面每条都写清：**是什么 → 证据在哪 → 怎么修 → 修完验证什么**。

### 11.1 阻断 #1：定时清理在「缩容到 0」时停摆 → 截图可能超过 24 小时才删

**问题事实**：
- 清理任务由 `backend/app/retention.py` 在**应用启动时**拉起后台线程，每小时扫一次（`backend/app/main.py:138`）。
- 云托管实例缩容到 0 后，容器被销毁，**后台线程随之停止**。
- 本版定档把最小副本设为 **0**（§3.1），意味着**夜里可能长时间没有实例在跑清理**。
- 后果：D37 承诺的「截图 24 小时内删除」在「实例长时间为 0」的窗口里**无法执行**，
  直到下一个人访问把实例唤醒、清理线程重新拉起才会补删。

**修复（配置层，不改代码）**：配置云托管**定时触发**，每小时访问一次 `/health` 保活。
官方支持「定时触发执行命令或访问 URL 地址」：
<https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/practice/trigger.html>

| 项 | 值 |
| --- | --- |
| 触发对象 | 服务 `qbl-api` 的 `/health` |
| 频率 | 每小时 1 次（TTL 22h + 每小时扫 ⇒ 删除 ≤23h 才成立） |
| 代价 | 每小时唤醒一次实例，按量计费极小（见 §5 的 C 行估算） |

**验证（部署后必做，记入 §12）**：
1. 看 `/app/var/log/deletion.log` 里有按小时的清理记录；
2. 造一个过期文件，等一个周期，确认被删且 `deletion.log` 有记录；
3. **临时把最小副本设 0、等 40 分钟无访问**，再访问唤醒，确认清理线程恢复运行。

> ⚠️ 给产品/合规的话：**「实例缩容期间删除会延后，唤醒后立即补删」**。
> 若合规要求「严格 24 小时整内删除，不许延后」，唯一稳妥做法是**最小副本 1 常驻**（多花约 32 元/月，见 §3.1）。

### 11.2 阻断 #2：容器内 SQLite + 缩容到 0 = 每次重建丢全部用户数据

**问题事实**（三条硬证据）：
1. 官方：「30min 内无流量则后台会将实例副本数缩容为 0」（[服务设置](https://developers.weixin.qq.com/miniprogram/dev/wxcloudservice/wxcloudrun/src/guide/service/pipeline.html)）；
2. 我们的数据库路径是容器内 `var/backend/qbl.db`（`backend/app/config.py:41`），开启 WAL（`backend/app/db.py:302`）；
3. 容器本地盘不持久（官方：每次发布都构建新镜像、新版本，容器是临时的）。

**修复状态：✅ 已定（个人助理 2026-11-03 代老板拍板）= 接受丢数据，0 元**

| 方案 | 动作 | 代价 | 状态 |
| --- | --- | --- | --- |
| **A. 接受丢数据** | 无 | **0 元**，**数据每次重建清零** | ✅ **已定，当前执行** |
| B. 开云托管 MySQL | 控制台开通 + 开发者把 `db.py` 切 MySQL + 迁移脚本 | 246 元/月 + 开发工时 | ⏸ 暂不做 |
| C. 外部 MySQL | 同上 | 价格待核实 | ⏸ 不采用 |

**执行要求（见 §4.2 的 🚨 红色说明）**：
- 部署回报里**必须写明「内测数据会丢」**；
- 把「重启后次数重置、历史清空，不是 bug」**告诉测试和前端**，防止当缺陷排查；
- 正式对外之前**必须**切 MySQL。

### 12.1 E4 冷启动的测法（写清楚，别糊弄）

```bash
# 1) 确认当前副本为 0（控制台看到实例数 0，或等 30min 无访问）
# 2) 用小程序或控制台「日志-调试」发起一次请求，记录时间 t1
# 3) 拿到响应后记录 t2，E4 = t2 - t1
# 4) 连测 3 次取中位数，写进 ops/evidence/cloudrun-coldstart.txt
```

> 冷启动数字要**和 OCR 数字分开报**：用户感知的总时长 = 冷启动 + OCR。
> 两者相加若接近 30 秒承诺线，要在群内明确写出来。
