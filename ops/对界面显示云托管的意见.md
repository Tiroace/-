# 对「界面显示已走云托管」建议的回复

> 提交人：运维｜时间：2026-11-03
> 回应：个人助理提出的验证口径（在界面显示「已走云托管」标记 / 环境 ID 后 4 位）

---

## 0. 结论

**方向对，但有个前提不能破：正式提审包里不能出现这个标记。**

建议做成**「只在开发/体验版显示」**，理由是提审截图和正式界面都不该出现技术串。
技术上完全可行，代码里已有现成的判断函数。

---

## 1. 为什么方向是对的

你说得对：`VITE_CLOUD_ENV` 没设或设错时，`hasCloudBackend()` 返回 false，
代码**会悄悄退回旧通道**——页面照样能出报告，但根本没走云托管。

这种「假通过」最难发现，比直接报错糟糕得多。界面上给个可见标记，
**运维、老板、测试者三边一眼能看出来，不用每次翻日志**，这个价值是真实的。

---

## 2. 为什么不能放进正式包

| 顾虑 | 说明 |
| --- | --- |
| 提审截图会带上 | 产品界面出现 `prod-1a2b3c` 这种技术串，审核员和平台都看得到，不合适 |
| 基础设施信息外露 | 环境 ID + 服务名可以拼出默认公网域名，虽然我们走内网不需要它，但没必要暴露 |
| 普通用户看不懂 | 对用户是噪声，不像一个「信息查询工具」该有的东西 |

---

## 3. 我建议的做法（技术已确认可行）

代码里 `src/src/common/config.js:22` 已经有现成的判断：

```javascript
export function hasCloudBackend() {
  return Boolean(CLOUD_ENV && CLOUD_SERVICE);
}
```

所以前端只要：

```javascript
// 建议位置：设置页 /「关于」页底部，不放在首页主视觉
// 只在非生产构建时渲染
if (hasCloudBackend() && process.env.NODE_ENV !== 'production') {
  // 显示：已连接云托管 · 环境 xxxx
}
```

具体形式二选一（前端定）：

| 方案 | 显示内容 | 优点 |
| --- | --- | --- |
| A | 「已连接云托管 · 环境 **3c4d**」（只显示后 4 位） | 不暴露完整 ID，能区分不同环境 |
| B | 「后端：**云托管**」（不显示 ID） | 最干净，只看通道对不对 |

**我倾向 B**——验证目的是「确认走没走云托管」，**不是确认走的哪个环境**；
环境 ID 对不对该在构建时由 `VITE_CLOUD_ENV` 本身保证，不该让界面来验。

---

## 4. 这个标记不能替代真正的验证

**界面标记只是「帮人眼快速判断」，不能当成部署验收的依据。**

真正能证明「请求真的走了云托管」的证据，还是这两条：

| 证据 | 怎么取 | 为什么更硬 |
| --- | --- | --- |
| **后端能查到这次请求** | 后端日志里有对应的 `/analysis` 请求记录 | 请求真到过后端，不是前端自己显示的 |
| **`ocr_parallel` / `ocr_images` 字段有值** | 查任务详情接口 | 这是后端真实执行记录，前端造不出来 |

**界面上写「已连接云托管」但后端没收到请求——这种可能完全存在**（比如前端显示了但调用失败走了降级）。
所以我会按原计划用后端证据做验收，界面标记当辅助。

---

## 5. 谁来做

这是**前端开发者的活**，不是运维的。我不改前端代码（职责边界）。
如果决定做，我建议提给前端时说明三点：
1. 只在非 production 构建显示；
2. 不显示完整环境 ID；
3. 放在二级页面（设置/关于），不进首页和报告页。

**优先级建议：低。** 它不解决部署问题，只是让日后排查快一点。
现在真正卡住的是环境 ID，那个更急。
