## 0. 一句话结论

一期（无大模型 / 无云 OCR / 微信首发）用**阿里云境内 ECS 单机 + Docker Compose** 起全套（api + MySQL 8 + Redis），对象存储放截图并设 24 小时生命周期自动删除，日志走云日志服务存 6 个月以上，成本按量档约 **每月 300–500 元量级**、包年档更低——**具体数字以 §7 为准，凡未取到官方单价的格子都标了「待核实」，我不填估计值**。

选型原则只有三条：
1. **同一云厂商、同一地域、同一主体**：服务器、域名、小程序备案必须同主体（见 `icp-备案材料清单.md`），同厂商能省掉跨厂商材料。
2. **能一台扛住就先一台**：一期日活量级下，MySQL/Redis 与 api 同机放得下；拆开要多付一份机器和网络费用。
3. **必须备案**：境内 ECS 且开公网带宽才能拿到备案服务码，所以机器必须包年包月 ≥3 个月，按量付费拿不到服务码。

## 2. 机型配置（按 OCR 实测）

### 2.1 已知的实测数据

| 指标 | 数值 | 来源 |
| --- | --- | --- |
| 单图 OCR 耗时 | 约 **4–5 秒** | 需求书 / Chief 任务说明（本项目既有实测口径） |
| 3 图并行目标 | **≤ 10 秒** | 同上（D22 速度门槛：单张 ≤4s / 3 张 ≤10s） |
| 引擎单条（不含 OCR） | **0.2–0.3 秒** | `docs/STATUS.md` 识别引擎一行 |
| 本机开发机 | i7-10510U / **4 核** / 7.8 GB RAM | 本次探测：`var/docker-probe.txt` |

### 2.2 核数怎么定的

OCR 是 **CPU 密集型 + 单图不可再拆** 的负载。并发能力取决于「同时能跑几张图」，而不是总核数除以线程数。

- RapidOCR/onnxruntime 单张图默认可占 `QBL_OCR_THREADS`（默认 8）个线程；在 4 核机上实测单图 4–5 秒。
- 要把 **3 张并行压在 10 秒内**，需要 3 个 OCR 任务同时跑且各自不被饿死。OCR 任务单张消耗的有效并行度约等于 1.5–2 核（线程数超过物理核心数后收益快速下降）。
- → **3 并发 × 2 核 = 6 核**，再给 MySQL/Redis/Nginx 与系统留 2 核 → **8 核**。
- 内存按「每并发 OCR 约 1–1.5 GB（模型 + 图片解码）+ MySQL buffer + 系统」估算，8 GB 偏紧，**16 GB** 为稳。

> **这条是推演，不是实测**：本项目尚无云上 OCR 压测数据。D5 有一次「OCR 并行 + 5s→4s/10s 门槛实测」，等实测结果回来，本节按实测改；若实测 4 核能压住 3 并发 10 秒，机型降到 4 核 8 GB，成本直接砍一半。

### 2.3 推荐规格（两档）

| 档位 | 规格 | 用途 | 说明 |
| --- | --- | --- | --- |
| **A. 起步（内测 10–20 人）** | 4 核 8 GB，ESSD PL0 系统盘 40 GiB | 内测期单机 | 够 1–2 并发；内测人数少、峰值低 |
| **B. 上线（推荐）** | **8 核 16 GB**，ESSD PL0 40 GiB + 数据盘 100 GiB | 正式上线 | 支撑 3 并发 OCR ≤10 秒目标 |

- 云盘一律 **ESSD PL0**：官方示例价 0.50 元/GiB/月（按量 0.00105 元/GiB/小时），是最便宜的一档，一期数据库 QPS 极低，PL0 足够。
- 系统盘 40 GiB 只放 OS 与镜像；**数据盘单独挂**，数据库/日志/上传都放数据盘，好处是扩容和快照按盘做，不和系统盘绑死。

## 3. 软件栈与部署形态

```
                ┌──────────────── 阿里云 ECS（8C16G，包年包月）────────────────┐
   用户 ── HTTPS ──▶ Nginx（80/443，强制跳转 + HSTS）                            │
                │      └─▶ api 容器（FastAPI，127.0.0.1:8000）                   │
                │              ├─▶ mysql 容器（8.4，仅容器网络，不映射公网）      │
                │              └─▶ redis 容器（7.4，仅容器网络）                 │
                │      数据盘 /data ← api_data / mysql_data / redis_data 卷      │
                └───────────────────────────────────────────────────────────────┘
   截图 ──▶ OSS Bucket（私有读，临时签名 URL）── 生命周期规则：24 小时自动删除
   日志 ──▶ SLS（应用日志 + Nginx 访问日志），保留 ≥ 180 天
```

- 编排文件：`ops/docker-compose.yml`（api + mysql + redis 三服务，全部只绑 127.0.0.1）。
- 本地已实际跑通（见 `ops/README.md`「本地验证记录」）。

### 3.1 MySQL 8

- 版本：`mysql:8.4`（LTS）。
- 字符集 `utf8mb4` / `utf8mb4_0900_ai_ci`，时区 `+08:00`，`max-connections=200`。
- 端口**不**映射到公网，只在容器网络内可访问；运维排障走 SSH 隧道。
- 现状说明：后端当前仍是 SQLite（`backend/app/db.py` 单层封装，D2 决定的原型期方案）。切 MySQL 要改这一层 + 迁移脚本，**属于开发任务，不在本次运维交付范围**，此处只保证库已按生产形态跑起来。

### 3.2 Redis 7

- 版本 `redis:7.4`，`appendonly yes`、`appendfsync everysec`。
- **生产必须设口令**：`REDIS_PASSWORD` 在 `.env` 里填，禁止空口令对容器网络以外的任何地址开放。

### 3.3 对象存储（截图）

- Bucket：`qbl-shots-<环境>`，**私有读**（ACL private），不开公共读。
- 上传：api 用 STS 临时凭证直传，前端拿临时签名 URL 访问，URL 有效期 ≤ 10 分钟。
- **生命周期规则（核心合规项）**：前缀 `shots/`，**对象创建 24 小时后自动删除**；另加一条 `abort-incomplete-multipart-upload` 7 天清理，防止分片残留。
- 不做版本控制（版本会阻止删除，和 24 小时规则冲突）。
- 后端已有对应配置项 `QBL_UPLOAD_TTL_HOURS=24`（`backend/app/config.py:53`），与 OSS 规则口径一致，双保险。

### 3.4 域名与 HTTPS

- 域名：备案通过后再解析到 ECS。
- 证书：云厂商免费 DV 证书（自签不行）。
- Nginx：80 → 301 到 443；启用 TLS 1.2/1.3；HSTS `max-age=31536000`；关闭 `server_tokens`。

## 6. 日志（保存 ≥ 6 个月）

**法律依据**：《网络安全法》第二十一条要求采取监测、记录网络运行状态、网络安全事件的技术措施，并**按照规定留存相关的网络日志不少于六个月**。

| 日志 | 采集 | 存储 | 保留 |
| --- | --- | --- | --- |
| Nginx 访问日志 | SLS Logtail | SLS Logstore | **180 天**（≥6 个月） |
| api 应用日志 | 容器 json-file → Logtail | SLS Logstore | **180 天** |
| MySQL 慢查询 / 错误日志 | Logtail | SLS Logstore | 180 天 |
| 管理后台操作日志（`admin_audit_log`） | 应用写入 DB | DB + SLS | **≥180 天**（D23 决定） |
| 容器日志（本地兜底） | json-file | 磁盘 | 单文件 10MB × 3 个（≈30MB/容器） |

- 容器日志只是**本地兜底**，真正的 6 个月留存靠 SLS；不依赖磁盘卷留着。
- 日志里**禁止**出现：完整手机号（按 `backend/app/community/privacy.py` 脱敏口径）、截图原文全文、密钥。
