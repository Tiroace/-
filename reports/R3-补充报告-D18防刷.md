## 一、D18 口径回顾

> **「可疑票收下、不计入展示、保留记录备查」**
> 不是入口拒绝，也不是静默丢弃。
> 投票接口照常返回成功，不给用户「你被风控」的提示，用户自己的「已投/可改」状态仍正常。

实现要点（实测确认）：
- `votes` 表新增 `counted`（默认 1）、`risk_reason`（`device_flood` / `ip_flood`）
- 窗口期 10 分钟；同设备超 5 票 → `device_flood`；同 /24 段超 20 票 → `ip_flood`
- 公开票数（`posts.vote_up/vote_down`）只统计 `counted=1`
- 后台 `GET /admin/community/votes?counted=0` 可查可疑票

## 二、四条断言结果：**全过**

### ① 同设备连投 6 票 → 展示不涨，但记录都在 ✅

| 断言 | 结果 |
| --- | --- |
| 6 次投票接口均返回 200（不拒绝、不提示被风控） | ✅ |
| `votes` 表**完整保留 6 票** | ✅ |
| 计入展示的票数 ≤ 设备阈值 5 | ✅ |
| `posts.vote_up` 与 `counted` 一致 | ✅ |
| 超出阈值的票标记 `counted=0` 且写了 `risk_reason` | ✅ |
| `risk_reason` 为 `device_flood` | ✅ |

### ② 不同设备 / 不同 IP → 正常计数 ✅

| 断言 | 结果 |
| --- | --- |
| 4 个不同设备各投 1 票，计入展示 = 4 | ✅ |
| 无一张被误判为可疑票 | ✅ |
| 不同 IP 段不受影响 | ✅ |

### ③ 改票不重复计数 ✅

| 断言 | 结果 |
| --- | --- |
| 同一用户改票 3 次，`votes` 总数仍为 1（不叠加） | ✅ |
| 改票后 `vote_up=0 / vote_down=1` 正确 | ✅ |
| **同一用户反复改票 8 次不会被误判为刷票** | ✅ |

> 第 3 条后半句很关键：如果风控按「请求次数」算而不是「票数」，
> 正常用户改几次票就会被标记成可疑票——实测没有这个问题。

### ④ 缺 `X-Device-Id` → 退回 IP 判断且不报错 ✅

| 断言 | 结果 |
| --- | --- |
| 不带头投票返回 200，不报错 | ✅ |
| 同 IP 连续投票时计入数不超过 IP 阈值 | ✅ |
| 命中时 `risk_reason` 为 `ip_flood` | ✅ |

## 三、额外验证

### 3.1 被风控用户仍能改票 ✅
最后一个被标记 `device_flood` 的用户改票返回 200，详情页可正常访问。
—— 符合 D18「用户自己的已投/可改状态仍正常」。

### 3.2 后台可查可疑票 ✅
`GET /admin/community/votes?counted=0` 返回 200，能查到可疑票记录。

### 3.3 不存明文设备号 ✅
查库确认 `votes.device_hash` 存的是摘要，不是明文 `X-Device-Id`（符合 §8）。

## 四、反向验证：断言确实依赖阈值，不是「恰好通过」

为了确认这 10 条用例不是「怎么跑都绿」，做了反向实验：

```
把 QBL_COMMUNITY_VOTE_DEVICE_LIMIT 设为 999（即关掉风控）
→ 同设备连投 6 票：总票 6、可疑 0、展示 6
```

风控未触发，**符合预期**。这说明：
- 测试断言确实依赖阈值逻辑，不是空转；
- 阈值可配置且真实生效。

## 七、结论

**D18 防刷口径按设计落地，G 组三项全部可封版。**

行为完全符合「收下、不计展示、保留记录」：

- 对运营：可查（后台能筛查可疑票）
