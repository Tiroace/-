## 二、D-07 复测：✅ 已修复

**原问题**：开关关闭时 POST 接口返回 400（body 校验先于 handler 执行），泄漏接口存在性。

**验证方式**：逐个打 8 个社区端点（4 GET + 4 POST），断言**全部 404**。

| 验证点 | 结果 |
| --- | --- |
| 8 个端点（GET + POST）一律 404 | ✅ |
| POST 带**完整合法 body** 也是 404（不能走到业务逻辑） | ✅ |
| 404 错误码与普通「资源不存在」一致 | ✅ |
| 关闭时不返回任何帖子数据 | ✅ |

> 关键补充用例 `test_带完整合法body也404`：即使 body 完全合法，
> 也必须 404——证明拦截发生在业务逻辑之前，而不是靠 body 校验失败碰巧挡住。

## 三、D-08 复测：✅ 已修复

**实现**（实测）：
- `GET /admin/community/posts?status=pending` —— 审核列表
- `POST /admin/community/posts/{id}/review` —— `{"action": "approve"|"reject"|"hide"}`

| 验证点 | 结果 |

| approve 后状态 `approved` 且出现在公开列表 | ✅ |
| reject 后状态 `rejected` 且不出现在公开列表 | ✅ |

| 不存在的帖子 404 | ✅ |

## 五、采纳前端的「新包校验」经验

前端提出：**只连上自动化、能截图，不足以证明模拟器加载的是新包**。
必须在断言前查一个「只有新包才有的节点」。

本报告的做法：
1. 断言 0 先用 `wx.createSelectorQuery().select('.hero-title').boundingClientRect()` 探测；
2. 文案断言**一律从编译产物读**（`pages/square/*.wxml`），不受运行层影响；
3. 两者结合，避免「产物对、模拟器旧」导致的假结论。

这条已写进断言脚本注释，作为后续 UI 验证的标准步骤。
