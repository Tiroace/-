# 缺陷单 · 社区开关关闭时前端入口未隐藏（前后端开关不一致）

| 项 | 内容 |
|---|---|
| **缺陷编号** | BUG-20261103-02 |
| **标题** | **社区开关关闭时前端入口未隐藏，前后端开关不一致** |
| **提出人** | 软件测试者 |
| **提出时间** | 2026-11-03 |
| **严重级别** | **P0**（产品经理认定；影响提审与被审核质询） |
| **状态** | 待修复（已派给软件开发者） |
| **关联需求** | 06 号 §八「社区相关页面确认未出现（开关关闭）」；路线令社区先关闭 |

---

## 一、现象

`QBL_FEATURE_COMMUNITY=0`（社区关闭）时：

- 首页底部 **tabBar 仍显示「广场」入口**，且可点击进入；
- 点进去后显示「广场还没开放」空态（页面本身无白屏、无 404）。

## 二、期望

按项目自身设计（`src/src/common/features.js` 第 4 行）：

> 前端策略是「**入口整个隐藏**」，不是显示「开发中」——所以这里不写死开关，而是以「探测后端是否开放」为准，避免两边开关不一致导致露出入口却点进去 404。

**即：社区关闭时，前端不得有任何可达入口。**

## 三、根因

| 层 | 现状 | 问题 |
|---|---|---|
| 后端 | `QBL_FEATURE_COMMUNITY=0` → `/community/*` 返回 404 | ✅ 正常 |
| 前端 tabBar | `pages.json` **静态写死三项**（检查 / **广场** / 我的） | ❌ 不会随开关变化 |
| 前端探测 | `probeCommunity()` **只在 `pages/square/index.vue` 内调用** | ❌ 点进去之后才判断，入口早已露出 |
| 隐藏实现 | 全仓检索 `hideTabBar` / `setTabBarItem` / `showTabBar` = **0 处** | ❌ 「入口整个隐藏」从未落地 |

**结论：设计写了「入口整个隐藏」，但实现只做了「点进去后显示空态」，前后端开关不一致。**

## 四、技术限制（决定修复方案）

微信小程序 **tabBar 无法运行时隐藏单个 tab**，只有：

| 方案 | 可行性 |
|---|---|
| A. `wx.hideTabBar()` 整组隐藏 | ❌ 会把「检查」「我的」一起藏掉 |
| B. 显示入口 + 空态 | ❌ **违反设计稿第 4 行，产品明确否掉** |
| **C. 提审构建整组去掉广场 tab** | ✅ **产品选定** |

## 五、修复要求（产品经理定，原文）

1. 提审构建的 `pages.json` 里 **tabBar 只保留「检查」「我的」两项**，广场页面 `pages/square/index` 不进 tabBar；页面文件可保留，代码不删。
2. **不采用**「显示入口 + 点进去空态」的方案。
3. **构建按环境区分**：提审构建无广场 tab；开发构建保留，便于后续开放时联调。**别把两套打包配置混成一个。**
4. 关闭 `QBL_FEATURE_COMMUNITY` 状态下：`/community/*` 仍返回 404（已有），**但前端不得有任何可达入口**。

## 六、验收标准

- [ ] 提审构建产物 `app.json` 的 `tabBar.list` **只有 2 项**：检查、我的；
- [ ] 提审构建中首页/我的页 **无任何**「广场」字样与入口；
- [ ] 开发构建产物 tabBar 仍为 3 项（保留广场，供后续开放联调）；
- [ ] 两套构建配置**分开**，不共用一个写死配置；
- [ ] 关闭状态下 `/community/*` 仍 404（回归，确认未破坏）；
- [ ] `postbuild-check` 与 `check:r1` 全绿；
- [ ] 06 号 §八 增加验收项：「前端不得有任何可达社区入口」。

## 七、影响

- **提审**：审核员若点进广场，会看到一个「不应存在」的入口，可能被质询「为什么有个不开放的入口」。
- **截图**：#01 首页截图中 tabBar 带「广场」，**该张不得作为提审材料提交**，需重新构建后重截。
- **用户观感**：入口露出但点进去是空态，与设计意图相反。
