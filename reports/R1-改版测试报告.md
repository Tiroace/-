## 三、发现的新缺陷

### D-02【P1】`source=llm` 但带 rule_id 的发现，绕过词库等级下限

| 项 | 内容 |
| --- | --- |
| 位置 | `engine/calibrate.py::_floor_for` |
| 现象 | 该函数只处理 `source == "rule"` 与 `source == "pattern"`；`source == "llm"` 即使带了合法的 `rule_id`，也直接 `return None`，**不做下限回拉** |
| 触发场景 | 大模型引用一条真实规则（rule_id 填对、证据也是原文），但把等级判轻。这是真实模型常见行为 |
| 后果 | 法规类问题被判绿，用户看到「没问题」 |
| 复现 | `pytest tests/engine/test_defect_D02_llm_floor.py` |
| 建议修复 | 把判断条件从「看来源标签」改成「看有没有 rule_id」：`if finding.get("rule_id"):` |

> 这是 D-01 修完后的**残留漏洞**：D-01 修的是 `source=rule` 的情况，漏了 `source=llm` 的情况。
> 端到端测试之所以一直是绿的，是因为 Mock 模型恰好把来源标成了 `rule`——又是「测试运气好」陷阱。

### D-03【P1】CLI 摘要行仍读 v1 字段，每次 analyze 都以 KeyError 崩溃

| 项 | 内容 |
| --- | --- |
| 位置 | `engine/cli.py` 第 93–103 行「[摘要]」打印语句 |
| 现象 | 仍在读 `report["risk_level"]` 与 `report["risks"]`，v2 已无这两个字段 → `KeyError: 'risk_level'` |
| 影响 | **报告文件本身是正确写出的**，崩溃发生在之后；但 CLI 退出码非 0，`scripts/run_engine.ps1`、CI、后端 `engine_runner` 若按退出码判成功会全部误判失败 |
| 复现 | `python -m engine.cli analyze --ocr-text data/testset/ocr/T001.txt --out x.json` |
| 建议修复 | 摘要改用 `overall` / `findings`；trace 的 `evidence_dropped` 兼容成 `findings_dropped` |
